# 解析适配器

> 写给：要新增语言支持或理解解析行为的开发者

> 最后更新：2026-11-14

## 适配器总览

解析层 `internal/parser/adapter` 按语言/精度选择适配器，产出统一 IR（类/方法/调用关系）：

| 适配器            | 精度    | 启用方式                        | 备注                                                                                                      |
| -------------- | ----- | --------------------------- | ------------------------------------------------------------------------------------------------------- |
| `treesitter`   | 中（默认） | 始终注册（兜底，无需配置）               | 正则启发式，31 语言，零 CGO；`-tags treesitter` 切真语法树；`treesitter.BuildVariant()` 返回当前实现标识（`regex` / `treesitter`），供基准报告区分 |
| `codegraph`    | 高     | `parser.codegraph.db` 配置    | 接 CodeGraph 索引库                                                                                         |
| `jcodeindexer` | 高     | `parser.jcodeindexer.db` 配置 | 接 JVM 专项索引器（Java/Kotlin/Scala）SQLite 直读                                                                 |
| `scip`         | 高     | `parser.scip.index_dir`     | SCIP index                                                                                              |
| `lsp`          | 高     | `parser.lsp.enabled: true`  | 按语言分发 gopls/jdtls/clangd/rust-analyzer/pyright-langserver/typescript-language-server；缺失自动回退 tree-sitter |

> **`parser.adapters`** **为声明性清单**：`internal/runtime/runtime.go` 的 `NewParserRegistry` 始终注册 tree-sitter（兜底），并按 `parser.lsp.enabled` / `parser.scip.index_dir` / `parser.codegraph.db` / `parser.jcodeindexer.db` 注册高精度适配器；`parser.adapters` 数组当前**不作为注册开关被消费**，仅作声明/文档登记（以代码为准）。

> **LSP e2e 运行环境（遗留② 已验证）**：`docker/lsp-test/Dockerfile` 已内置 Java/C++ 的 LSP 服务器——`jdtls`（Eclipse JDT LS 快照，依赖 `default-jdk`，debian:trixie 默认 JDK 即 21，满足最新 jdtls 快照的 class file 65.0）与 `clangd`（含 `clang`/`compile_commands.json` 能力），可实跑 Java/C++ LSP 端到端测试；此外含 gopls / rust-analyzer / pyright / typescript-language-server / scip / codegraph 等工具。

> **`jcodeindexer`** **已接入（2026-09-03）**：`internal/parser/adapter/jcodeindexer` 实现 BatchParser，直读 JCodeIndexer（第三方 JVM 专项索引器）的 SQLite 库——`symbols` + `edges` 契约（符号 + 调用图），按文件分组产出 IRDocument；`runtime.NewParserRegistry` 在 `parser.jcodeindexer.db` 配置（且非默认值）时注册，JVM 语言（java 优先）走高精度，失败自动回退 tree-sitter。schema 不匹配 / 库缺失显式降级，绝不静默返回空 IR。此前文档「仅配置预留、未实现」表述已更正。默认值常量 `config.DefaultJCodeIndexerDB = "./jcodeindexer.db"`。

## ⚠️ CallerFQN 行为（影响面分析的关键）

- **建边条件**：`internal/analyzer/analyzer.go` 仅当 `call.CallerFQN != ""` 才建立调用边。

- **Go（默认 tree-sitter 正则路径，`adapter.go`，即** **`-tags`** **默认构建）**：`da20964` 修复回填了调用方 `CallerFQN`（Go 专属方法作用域跟踪，`detectCalls` 的 `caller` 参数为当前方法 FQN）。但回填的 FQN 曾为**裸名**（如 `Watcher.ReloadNow`），与查询用的包限定全名（如 `config.Watcher.ReloadNow`）**命名空间错位**，impact 仍恒空。`T1`（2026-09-02）在 adapter 中以 `package` 声明为前缀产出包限定 FQN（`config.Watcher.ReloadNow`；自调用 `w.ReloadNow` 经 receiver 变量识别限定为 `config.Watcher.ReloadNow`），并在 analyzer 加双向归一化，至此 **`impact`** **/** **`tests`** **/** **`get_call_graph`** **对 Go 默认真实可用**。

- **非 Go 语言（默认正则路径）**：`detectCalls` 对其它语言传 `caller`（来自当前方法作用域，无则空），caller/callee 默认走裸名启发式；**P19（2026-09-03）补齐显式包声明的三类语言包限定**——Java `package`、Kotlin `package`、C# `namespace` 在解析时捕获并作为 `caller` FQN 前缀（`com.example.OrderService.createOrder`），对齐 Go 的包限定命名空间；callee 因依赖类型消歧保持裸名。Python（以文件路径推导模块）、TypeScript（`import/export` 非包声明）、Rust（嵌套 `mod` 树）、C++（命名空间可多段嵌套）按「语种类别逐步收敛」留待后续。analyzer 双向归一化保证查询鲁棒。
  - **方法体语句抑制（2026-11-14）**：Java/Groovy 的方法模式无行首锚点且类型组允许空白，曾把 `return helper(a);` 读成「返回类型 return + 方法名 helper」——方法数虚增，且该行被 `continue` 吞掉后方法体内调用边全部丢失（公开基准 Java 真值为 0 的根因）。现以行首语句关键字（`return/new/if/for/...`）判定语句行，不参与方法声明解析，语句行继续进入 `detectCalls`。
  - **Java 方法模式重写（2026-11-14，R5-8 连带）**：改为行首锚定 + 修饰符可省略，修复两类漏解析——JUnit 5 的包级可见性方法（`void initCreationForm()`），以及单 tab 缩进（旧模式中修饰符组会吃掉唯一空白）。类型组改为「至少一个非空白字符起头」，避免 `helper();` 被当作「空类型 + 方法名 helper」。

- **LSP / SCIP / CodeGraph / JCodeIndexer 适配器**：由对应适配器回填 `CallerFQN`，跨语言可用。

## LSP 精度与生命周期（2026-11-14，P0-2）

- **分层符号**：initialize 声明 `hierarchicalDocumentSymbolSupport`，并按负载形状区分 `DocumentSymbol[]` 与 `SymbolInformation[]`（旧实现先试后者会「空字段反序列化成功」，导致容器名与层级静默丢失）。
- **容器限定 FQN**：容器名逐层拼接为 `ClassIR.FullName` / `MethodIR.ClassFQN`；gopls 的 `(*Calculator).Add` 与扁平 `containerName` 两种形态统一还原为 `Calculator.Add`，方法不再因 `ClassFQN` 为空被 store 丢弃。
- **调用边**：服务器声明 `callHierarchyProvider` 时，对每个方法的 `selectionRange` 起点执行 `prepareCallHierarchy` + `outgoingCalls`，产出 `CallIR`；同文件 callee 优先映射到本地方法 FQN，跨文件回退按 detail 解析接收者。单文件上限 **64** 个方法（`maxCallHierarchyMethods`），避免 O(N) 往返放大解析延迟；不支持该能力的服务器仅出符号。
- **空结果回退**：非空源文件解析出 0 个符号（如 clangd 缺 `compile_commands.json`）时返回 `ErrSourceUnavailable`，由 `FallbackParser` 回退 tree-sitter，不再静默固化空 IR 并写 hash。
- **进程生命周期**：`Close` 先发 `shutdown`（请求）+ `exit`（通知），再关 stdin，随后 `cmd.Wait()` 回收（2s 未退出则强杀）；`parser.Registry.Close()` 统一关闭已注册适配器，`ScanRepository` 与 watch 停止回调负责调用，避免遗留 gopls/jdtls 孤儿进程。初始化失败路径同样 Kill + Wait 并清理 pending。


- 小结：默认栈下 **Go 的影响面分析已可用（T1 命名空间对齐后）**；非 Go 走裸名启发式，双向归一化保证查询鲁棒。（历史上默认路径全空属缺陷，已修复，非设计行为；`adapter.go` 与 `adapter_ast.go` 双路径均已对齐 `CallerFQN` 回填，T1 进一步补齐默认路径包限定、**P20（2026-09-03）将同一包限定对齐到** **`adapter_ast.go`（真语法树路径）**——即 Java/Kotlin/C# 无论默认正则还是 `-tags treesitter` 都产出 `com.example.OrderService.createOrder` 形态的 caller。）

## Go 包级函数与服务端入库（合成包级容器，2026-11-14）

- 默认正则路径对无 receiver 的 Go 顶层函数不再留空 `ClassFQN`：解析时置为当前 `package` 名，并在文件末尾追加一个合成容器 `ClassIR{FullName=package, Type="PACKAGE", StartLine=1, EndLine=EOF}`。
- 三后端（FileStore/SQLite/PG）均按 `ClassFQN`→`Class.FullName` 关联方法，因此容器使包级函数可正常入库；方法 FQN 形如 `pkg.Func`，与调用图 `CallerFQN`（`pkg.Func`）命名空间对齐，不再产生悬空调用边。
- 同一文件已有同名类型时不重复创建容器（避免类映射冲突）。
- **AST 路径（`-tags treesitter`）已对齐（2026-11-14）**：`adapter_ast.go` 同样合成 PACKAGE 容器，按 AST receiver 字段确定方法归属（不依赖遍历顺序），caller/callee 使用 `pkg.Func` / `pkg.Type.Method`；进入 class/method 节点时保存并在离开子树后恢复作用域，嵌套类/嵌套函数之后的兄弟声明不再被错挂到内层作用域。同时补齐 `EndLine`（语法节点结束行）与 Go 的 `FieldIR`（struct 字段）/`ConstantIR`（包级 `const`），使两条路径产出一致。

## 跨文件接收者方法入库（2026-11-14）

- Go 允许在同一包的不同文件中为同一类型定义方法：`type Service struct{}` 在 `service.go`，
  `func (s *Service) FindTestLinks` 在 `testlink.go`。两条解析路径都把
  `MethodIR.ClassFQN` 置为接收者类型（`Service`），但该类型不在当前文件的 `Classes` 里。
- 三后端按「本文件 `ClassFQN` → classID」映射入库，映射不中即 `continue` 丢弃方法——
  该类方法对 `/context`、检索、调用图、测试关联**全部不可见**。
- 修复：`parser.EnsureMethodOwners` 在 scanner 入库前为未命中的 `ClassFQN` 补一条最小
  `ClassIR{FullName=ClassFQN, Type="CLASS"}`，方法自身 FQN 不变（仍为 `Service.FindTestLinks`）。
  类记录按文件隔离，不产生跨文件唯一性冲突；两条解析路径共用该归一。
- 排查要点：IR 层能看到调用边（`svc.FindTestLinks`），但 store 层没有同名方法——
  差异不在调用解析，而在方法归属。基准残余 FN 的 `Service.FindTestLinks` /
  `MCPServer.serveStdio` 均由此产生。

## 变量 / 常量 IR（2026-09-03 新增，Go 两条解析路径均已支持）

- 默认正则路径（`adapter.go`）与 AST 路径（`adapter_ast.go`）在产出 `ClassIR`/`MethodIR`/`CallIR` 之外，新增两类 IR，随 `UpsertIR`/`BulkUpsert` 自动落库（仅 PG 后端 `field`/`constant` 表，见[存储后端.md](存储后端.md)）：

  - **成员变量** → `FieldIR{ClassFQN}`：`type X struct { ... }` 体内的字段行（含 tag 行，tag 剔除后取类型）；仅非方法体内提取。

  - **包级常量** → `ConstantIR{FilePath}`：`const X [Type] = v` 单行与 `const ( ... )` 块内行；方法内 `const` 忽略（局部常量不入库）。

- **已知坑（T 修复）**：`const ( ... )` 块的闭合行 `)` 必须在 `constBlock` 激活时进入常量分支，否则 `constBlock` 无法复位，会吞掉其后所有行（含 struct 字段行，导致 `Fields` 恒空）。

## 新增一个适配器

1. 在 `internal/parser/adapter/<name>/` 实现 `Adapter` 接口，产出 `parser.MethodIR` / `CallIR`（**务必回填** **`CallerFQN`**）。
2. 在 `cmd/codeschema` 的分发处接线（受 build tag 约束时加对应 tag）。
3. 在配置 `parser.adapters` 文档与示例里登记（`parser.adapters` 为声明性清单，运行时注册由 `parser.lsp.enabled` / `parser.scip.index_dir` / `parser.codegraph.db` 驱动，见上文）。
4. 补单测（真实语言工程验证），同步更新文档与 `make counts`（若新增包）。
