# 存储后端

> 写给：要切换/扩展存储的开发者

> 最后更新：2026-11-14

## 统一接口

`internal/store.Store` 抽象所有存储操作（Upsert/Get/Tag/Search/HealthCheck…）。后端经 `cmd/codeschema` 的 build-tagged 分发接线——因 `pg`/`redis` 子包反向依赖 `store` 包，分发必须落在 cmd 层，不能在 `store.NewStore` 内（否则循环依赖）。

## 四种后端

| 驱动              | 配置                                               | 构建标签          | 说明                                       |
| --------------- | ------------------------------------------------ | ------------- | ---------------------------------------- |
| `file`（默认）      | `storage.driver=file`                            | 无             | JSON 文件，零依赖，跨会话弱                         |
| `sqlite`        | `storage.driver=sqlite`                          | 无             | modernc.org/sqlite 纯 Go 免 CGO，关系查询/跨会话一致 |
| `pg`/`postgres` | `storage.driver=pg` + `storage.dsn=postgres://…` | `-tags pg`    | PostgreSQL，亿级横向扩展                        |
| Redis 缓存层       | `storage.kv=redis://host:6379/0`                 | `-tags redis` | 热点类/调用 L2 缓存（CacheReader 反查），空则不启用       |

### Redis 命名空间与生命周期（2026-11-14 落地）

多租户/多实例可能共用同一 Redis，键必须隔离且不能永久驻留：

- **键前缀**：所有键统一加命名空间前缀，默认 `codeschema:`；`cmd/codeschema/store_redis.go` 按 `sha256(storage.driver + "|" + storage.dsn)` 前 6 字节派生 `codeschema-<12hex>:`，不同租户/存储实例互不覆盖。键形如 `<ns>class:<fqn>` / `method:` / `classpath:` / `methodpath:` / `caller:` / `callee:` / `file:`。
- **TTL**：类/方法/反查索引写入后统一设置 `Expire`，默认 **24h**；索引可由主存储重建，过期即可自愈，避免删除/重建后残留键永久占用内存或返回陈旧数据。
- **Flush**：`rebuild-kv` 的清理改为按 `<prefix>*` 游标 `SCAN` + `DEL`，**绝不使用 `*` 清库**，只影响本命名空间。
- **扩展**：需要共享命名空间/自定义 TTL 时用 `redis.NewRedisCacheWithNamespace` / `NewRedisCacheFromURLWithNamespace`；测试可用 `kvBackend` 内存实现，无需真实 Redis。

## Schema 一致性说明（改库前必读）

运行时 **不会加载** `internal/store/migrations/001_init.sql`（其定位为设计参考，非执行 DDL）。各后端 schema 以内联 DDL 为准，且**后端之间并不一致**：

- **默认 SQLite**（`internal/store/sqlite/sqlite.go`）：**FQN 型轻量 schema**（file/class/method/call/tag/class\_tag/method\_tag），类继承用 `class.parent_fqns`(JSON)，`call` 用 `caller_fqn/callee_fqn`(文本)，**无** project/class\_parent/parameter/ret\_type/method\_test\_link 表。

- **PG**（`internal/store/pg/pg.go`）：**14 表 ID 型**（含 project/class\_parent/parameter/ret\_type/method\_test\_link，以及 2026-09-03 新增的变量表 `field`、常量表 `constant`），`call` 同样用 `caller_fqn/callee_fqn`（与 001\_init.sql 的历史 `caller_method_id` 版不同，以代码为准）。

- 影响面/调用链均以 **FQN 串接**（caller\_fqn→method），而非 method id 外键。

- **FK 约束（2026-09-03 落地，仅 PG）**：必填且必有目标的列加 `FOREIGN KEY ... ON DELETE CASCADE`（file.project\_id / class.file\_id / method.class\_id / parameter.method\_id / ret\_type.method\_id / call.file\_id / class\_parent.class\_id / class\_tag.\* / method\_tag.\* / method\_test\_link.\* / field.class\_id·method\_id / constant.file\_id·class\_id）；删除 file/class/method 时级联清理从属数据。可空兜底列不加 FK（`class.parent_class_id` 靠 parent\_fqn 兜底、`call.caller/callee_fqn` 为 FQN 文本）。

- **field / constant 归属二选一**（CHECK 约束）：field 只挂 class（成员变量）或 method（局部变量）之一；constant 只挂 file（包/文件级）或 class（类级）之一。类级常量可复用 field(is\_const=1)。注意 DDL 用 `CREATE TABLE IF NOT EXISTS`，**仅对新建库生效**，既有旧库需手工 `ALTER TABLE ADD CONSTRAINT` 迁移。

- **field/constant 读写接口**（可选接口 `store.FieldConstantStore`，仅 PG 实现）：`UpsertClassFields`/`UpsertMethodFields`/`GetClassFields`/`GetMethodFields` + `UpsertFileConstants`/`UpsertClassConstants`/`GetFileConstants`/`GetClassConstants`，Upsert 为按归属全量替换。调用方用 `store.FieldConstantStore` 类型断言探测（同 `CacheReader` 范式），未命中回退。**cmd 层 Redis 包装（`redisCacheStore`）已透传该接口**（2026-09-03 落地）：不缓存、仅转发到底层 PG，底层未实现时返回错误由调用方回退。FileStore/SQLiteStore 未实现。

> 需跨后端共用而改 schema 时：同步修改 `001_init.sql`、`sqlite.go`、`pg.go` 三处内联 DDL，避免文档与代码漂移。
> 其余行为级变更（`UNIQUE(project_id, absolute_path)`、`method.return_type`/`ret_type` 归一化等）属破坏性改动，按 AGENTS.md 需先评审 + 回归后再落地。

## 写入性能事实（`scalebench` 实测，N=10万）

- 逐文件 `UpsertIR`：SQLite ≈ **77–237s**（事务提交放大），JSON FileStore ≈ **0.4s**（慢约 500×）。

- **已用** **`BulkUpsert`（单事务 + 预编译）修复**：100k 落库降至约 **5–14s**（约一个数量级提速）。

- 结论：生产化用 `BulkUpsert`；超大仓/亿级切 PG；**「SQLite 慢于 JSON」是写入事实，但 SQLite 的关系查询/一致性是 JSON 不具备的**。

- **PG 大规模实测（P23，2026-09-03 起 scalebench 新增 `pg_upsert`/`pg_bulk` 两列**，`-tags pg`）**：逐文件 `UpsertIR` 走网络 + 每文件独立事务，成本显著高于 SQLite 纯本机落盘（N=10k ≈ 155s）；`BulkUpsert`（单事务批量）把 10k+ 灌入压到近线性（N=10k ≈ 197s，量级低于 UpsertIR）。关系型后端横向扩展收益在**多实例/分库 + 索引 + CONCURRENT 建索引**，而非本机单进程吞吐；超大仓生产化应把「扫描→待入库批量」交给单个 worker 用 `BulkUpsert` 落 PG，查询/影响面走 PG 索引。

## 标签与检索

- 标签分类六类：`layer`/`biz`/`tech`/`risk`/`test`/`lang`，由 `DeriveTagCategory` 统一推导（三后端共用口径）。

- 检索：`fts`（全文，纯 Go 实现）+ `semantic`（向量）+ 融合重排；置信度低于 `min_score` 的结果被过滤（见[架构师文档](../02-架构师/README.md)）。

## 向量后端语义（R6-3）

- **删除隔离（P2-17）**：`ChromemStore.Delete` 调用 chromem-go 的 `Collection.Delete`，同时移除内存文档与持久化文件；删除后 `Search` / `Size` / `ListIDs` 不再返回该 ID，重启也不会复活。`Search` / `QueryText` 会把 Top-K 收敛到集合实际文档数（chromem 要求 `nResults <= Count`），删除后请求较大 K 不再报错。
- **模型/维度校验（P2-16）**：文件 `PersistentStore`（`vector.json`）写入 `model_id` 与 `dim`；加载时与当前 embedder 比对，不一致直接报错（`dimension mismatch` / `model mismatch`），避免切换模型后旧向量与查询向量不同空间、余弦恒 0 或结果静默错配。旧版文件无元数据时按实际向量长度推断维度，相符才加载并在下次保存时补写元数据；文件内向量长度与声明维度不一致同样拒绝加载。运行时装配见 `runtime.NewSearcherWithStore`：ONNX 记 `onnx:<embedding_model>`，降级统计模型记 `local-tfidf-v1`。
- **ONNX 生命周期（P2-16）**：`ONNXEmbedder.Close` 释放 session 后，`Embed` 返回 `onnx embedder is closed` 错误（不再对 nil session 触发 SIGSEGV），重复 `Close` 幂等返回 nil；全局单例 `CloseGlobalONNXEmbedder` 之后可再次 `GetONNXEmbedderGlobal` 重建。

## FileStore 持久化语义（R3-12）

- **原子写**：`store.json` 先写 `store.json.tmp` → `fsync` 内容 → 原子 `rename` → `fsync` 目录，最后删除临时文件。进程被强杀/掉电后只会看到完整的旧版本或完整的新版本。
- **损坏即失败**：`store.json` 解析失败时 `Open` 返回错误（不再静默当空库），避免下一次写入覆盖唯一副本；修复手段是人工还原备份或移走损坏文件后重建索引。
- **并发**：进程锁（`lock.Acquire`）防止 scan/serve 同目录并发写；内存态读写由 `FileStore.mu` 串行化。

## 连接池上限（R3-11）

`storage.max_open_conns` / `storage.max_idle_conns` 作用于 sqlite/pg 的 `database/sql` 连接池，默认 **16 / 8**；`0` 表示沿用 database/sql 默认（不限制），`file` 后端忽略。非法值（负数、idle > open）在启动校验阶段直接报错。

> 多租户：每个租户实例各自持有一个存储与连接池，PG 总连接数约为 `租户数 × max_open_conns`；41 租户默认配置约 656 条，超过 PG 默认 `max_connections=100` 时需调低本值或在 PG 侧启用 PgBouncer。

## 热点索引（R3-10）

- `call(file_id)`：按文件清调用（`DeleteFile` / 重索引 / `GetCallsByFileID`）。
- `class_tag(tag_id)` / `method_tag(tag_id)`：`search_by_tag` 反查；两张关联表 PK 前导列是 `*_id`，`tag_id` 无覆盖，缺索引即全表扫描。
- 三处 DDL 已同步（`internal/store/sqlite/sqlite.go`、`internal/store/pg/pg.go`、`internal/store/migrations/001_init.sql`）。SQLite 每次 `Open` 重放 `CREATE INDEX IF NOT EXISTS`，既有库自动补索引；PG 需调用一次 `InitSchema`（服务启动时执行）。

## 重索引语义（R3-1）

- 三后端统一「按文件全量替换」：新 IR 的类/方法/调用/imports 即使为空，也清空旧行，
  不留孤儿；未变更文件不触发写入。
- 删除顺序固定为「method_tag → method → class_tag → class」；SQLite 无 FK CASCADE，
  反过来先删 class 会让按 `class_id` 的子查询删不到方法。PG 依赖 `ON DELETE CASCADE`，
  但仍显式先清 method 再清 class，语义与 SQLite 对齐。
- `DeleteFile` 的 method_tag 以 **method ID** 为键清理；历史实现误用 class ID，会残留标签。
- 回归：`TestFileStore_ReindexRemovesStaleMethods` / `TestSQLite_ReindexRemovesStaleMethods` /
  `TestSQLite_BulkUpsertRemovesStaleMethods` / `TestPGStore_ReindexClearsWhenEmpty`。
- 修复后，第二轮 IR 无调用时 `GetCallsByFileID` 返回 0（修前残留 1 条）；
  `UpsertClasses` 公开路径旧类方法数由 1 收敛为 0。

## 落盘权限

- 所有持久化写入统一经 `internal/fsperm`：目录 `0700`、文件 `0600`（底层复用
  `pathsafe` 的权限原语）。
- 迁移：旧版本产生的 `0755` 目录 / `0644` 文件会在下次创建或重写时 `chmod` 收敛；
  SQLite `.db` 在打开（PRAGMA 建库）后立即收敛到 `0600`。WAL/SHM 由 SQLite
  按 umask 创建，依赖所在目录 `0700` 隔离。
