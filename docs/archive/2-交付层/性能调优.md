## 1. 关键性能指标

| 指标 | 关注点 |
|---|---|
| 扫描耗时 | 大仓库 < 5min 可接受 |
| 索引构建耗时 | 通常 < 扫描耗时 |
| 搜索 P95 延迟 | 目标 < 500ms |
| 内存占用 | 基准 ~100MB，索引加载后增加 |
| 磁盘占用 | 约占仓库大小的 5-10% |

## 2. 调优参数

| 参数 | 默认 | 建议 |
|---|---|---|
| `scanner.workers` | 4 | 小仓库 4-8，大仓库 8-16 |
| `storage.search.vector_dim` | 1024 | 低内存降到 128，内存约减 8 倍 |
| `watcher.debounce_ms` | 300 | 越小响应越快但触发越频繁 |
| `watcher.use_fsnotify` | false | 原生监听比轮询高效 |
| `scanner.file_size_limit_mb` | 10 | 大仓库收紧到 5 |
| `scanner.line_count_limit` | 50000 | 大仓库收紧到 10000 |

命令行示例：
```bash
./codeschema scan --workers 16 ./large-repo
./codeschema watch --fsnotify --debounce 200 ./repo
```

## 3. 不同规模仓库配置

**小仓库（< 1,000 文件）**：`workers:4`、`vector_dim:1024`。内存 ~50-100MB，扫描 < 1s。
**中型仓库（1k-50k）**：`workers:8`、`vector_dim:512`。内存 ~100-300MB，扫描 1-30s。
**大型仓库（50k-500k）**：`workers:16`、`file_size_limit_mb:5`、`line_count_limit:10000`、`vector_dim:256`、或 `semantic:false`。内存 ~300-800MB，扫描 30s-5min。

## 4. 内存优化优先级

1. 关闭语义搜索（最有效）：`storage.search.semantic:false`，仅保留 FTS。
2. 降低向量维度：`vector_dim` 1024→512→256→128。
3. 限制并发：`scanner.workers:2`。

## 5. 基准测试（闭环验证）

```bash
make bench   # 内置 Benchmark（ScanAndIndex/Search/FullPipeline）
# 多仓库对比（非 Benchmark，需环境变量）
set CODESCHEMA_BENCH_REPOS="C:\repo1;C:\repo2"
go test -run=TestMultiRepo_CollectMetrics -timeout 600s ./internal/integration/
```

**已知基准**（dev/ 规模决策已校正，超大 10 万文件数据见技术设计 §4）：
| 仓库 | 文件数 | 扫描 | 索引构建 | 搜索 P95 |
|---|---|---|---|---|
| CodeSchema 自身 | 81 | 87ms | 12ms | 1.99ms |
| 中型仓库 | 312 | 190ms | 21ms | 2.99ms |

扩展性：4x 文件量 → 约 1.6x 扫描 / 1.9x P95，线性扩展性良好。
> 极大规模（10 万+）：必须用 `BulkUpsert` 单事务批量写入（100k 落库 ~5-14s，多事务逐文件需 77-237s），详见 [技术设计文档 §4](../1-生产层/技术设计文档.md)。
