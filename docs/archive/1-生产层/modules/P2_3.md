# P2_3 文件监听 Watcher

> 模块编号：P2_3 ｜ 父模块：P2 编排层 ｜ 完成度：100% ｜ 代码：`internal/watcher`

## 🎯 模块用途

提供仓库文件变更的**双模式监听**：fsnotify 原生事件监听（低延迟）与轮询监听（跨平台兜底）。负责把「文件系统事件」转译为「待处理路径」，经防抖后交给 Scanner 增量处理，实现索引随代码编辑实时更新。

## 🧱 拆分逻辑说明

按**职责边界（变更发现者）**独立：Watcher 只负责「感知变化」，不负责「怎么处理」（Scanner）、不负责「何时处理」（Scheduler）。两种模式（fsnotify/轮询）实现同一 `Watcher` 接口，可运行时切换，这也是独立成模块的收益——新增监听模式（如 git hook）只需实现接口。

## ⚙️ 技术说明

**技术选型**：`github.com/fsnotify/fsnotify`（原生监听）+ 自研轮询（`time.Ticker`）；依赖 `internal/scheduler` 做防抖合并。

**对外接口契约**：
- `Watcher` 接口：`Start(ctx) error`（阻塞监听，优雅关闭由 ctx 驱动）
- `NewFsWatcher(root, scanner, sched, ignoreDirs)` — 原生监听
- `NewPollWatcher(root, scanner, sched, interval, ignoreDirs)` — 轮询监听
- 忽略目录配置（`Watcher.IgnoreDirs`，如 `.git`/`node_modules`）

**依赖的下层模块**：P2_2 Scanner（变更处理回调）、P2_4 Scheduler（防抖合并）、P8_6 健壮性（超时/恢复）、`fsnotify` 第三方库。

**数据模型**：无自有模型；事件 → 路径字符串流。

## 🔄 替代方案

- 纯 fsnotify：Linux 上 `inotify` 有 fd 上限、某些网络文件系统不支持，轮询作为兜底是生产必要。
- `git fsmonitor` 接入：更快但绑定 git 场景，当前双模式已覆盖非 git 仓库。

## 🚧 阻塞与风险

- fsnotify 在大仓库/网络盘上事件可能丢失或超限，轮询模式作为保底；生产建议 `--fsnotify` + 定期全量 `scan` 兜底。
