## 1. 三层存储架构概览

| 存储层 | 技术选型 | 用途 | 阶段 |
|---|---|---|---|
| 关系型数据库（权威源） | FileStore（P0）→ SQLite（P1）→ PostgreSQL（P2） | 全量结构化数据，事务性写入 | P0 |
| KV 缓存（热读） | Redis | 高频查询加速，低延迟访问 | P2 |
| 向量库（语义检索） | chromem-go（P2）→ Milvus（P3） | 语义相似度搜索 | P2 |
| 全文检索 | PersistentFTS（纯 Go，P1） | 精确符号搜索（零 FTS5 依赖） | P1 ✅ |

**P0 阶段实现 Store 接口 + FileStore（JSON 文件存储）**，后续可切换为 SQLite/PostgreSQL。Redis 和向量库在 P2 阶段接入。

## 2. 事务边界与隔离级别

| 操作 | 事务边界 | 隔离级别 | 说明 |
|---|---|---|---|
| 单文件解析入库 | 1 个文件 = 1 个事务 | `IMMEDIATE`（SQLite） | 避免 `INSERT OR UPDATE` 竞争 |
| 全量扫描 | 每文件独立事务 | `IMMEDIATE` | 大文件不阻塞其他文件 |
| 重建 KV | 1 个事务 | `DEFERRED` | 只读操作，允许并发 |
| 反向引用重建 | 1 个事务 | `EXCLUSIVE` | 写操作，不允许并发 |

**P2 PostgreSQL 迁移时**：使用 `READ COMMITTED` 隔离级别（默认）；大文件分批写入，使用 `SAVEPOINT` 支持部分回滚；使用 `LISTEN/NOTIFY` 实现跨进程索引变更通知。

## 3. 并发安全措施

- `file` 表的 `UNIQUE(absolute_path)` 约束防止重复插入。
- 每个 `ProcessFile` 独立事务，避免大事务持锁。
- 构建反向引用索引时使用读写锁保护共享缓存。

## 4. upsertIR 增量入库算法

`upsertIR` 对一个文件的 IR 执行增量入库，核心步骤：

1. 查询该文件现有所有 class/method 记录。
2. 将新 IR 的 class/method 与旧记录按 (行号区间 + 名称) 匹配。
3. 匹配成功的 → UPDATE（保留 id，刷新行号/签名/doc）。
4. 旧库有但新 IR 无的 → DELETE（级联清理关联子表）。
5. 新 IR 有但旧库无的 → INSERT。
6. 行号区间不重叠但全限定名一致的 → 视为重定位，UPDATE 行号。

**匹配判定表**：

| 新 IR 实体 vs 旧库实体 | 判定 | 动作 |
|---|---|---|
| 行号区间重叠 + 名称一致 | 同一实体 | UPDATE（保留 id，刷新行号/签名/doc） |
| 旧库有 / 新 IR 无 | 已删除 | DELETE（级联清理子实体） |
| 新 IR 有 / 旧库无 | 新增 | INSERT |
| 区间不重叠但全限定名一致 | 重定位（rename/move） | UPDATE 行号（结合 git diff 行号平移辅助） |

**行号区间重叠判定函数**：

```go
func intervalsOverlap(aStart, aEnd, bStart, bEnd int) bool {
    return aStart <= bEnd && bStart <= aEnd
}
```

**处理顺序**：先处理 file 行（INSERT OR UPDATE）→ 再处理 class（匹配→UPDATE/DELETE/INSERT）→ 然后处理 method（同 class 逻辑）→ 最后处理 call（先清空该文件旧调用边，再插入新边）。参数/返回类型/标签级联跟随 method ID 变更。

## 5. 开发指南

1. **定义 Store 接口**：在 `internal/store/store.go` 中定义统一的 `Store` 接口，包含所有存储操作。
2. **实现 FileStore**：在 `internal/store/filestore.go` 中实现基于 JSON 文件的轻量存储：
   - 内存 map 存储 + 定时/Close 时持久化到 JSON 文件。
   - 支持 UpsertFile、GetFileByPath、DeleteFile、UpsertIR 等核心操作。
   - 支持分析器查询接口：GetAllFiles、GetClassesByFileID、GetMethodsByClassID、GetCallsByFileID。
   - 使用 `sync.RWMutex` 保证并发安全。
   - **并发安全加固（2026-08-15，T2-4）**：`Open` 获取进程级文件锁（Unix `flock` 排他 / Windows 独占创建锁文件 `store.lock`），同一 store 目录被多进程（如 scan 与 serve 并发打开）时后者显式失败而非静默损坏 `store.json`；落盘为「tmp 临时文件 + `os.Rename` 原子替换」（防写一半）；`scanner.listFiles` 同步忽略 `store.json`/`store.lock`/`store.db` 数据文件（防 store 目录在仓库根时被当作源码收录）。
3. **实现 UpsertIR**：增量入库主逻辑，处理新增/修改/删除/重定位四种情况。
4. **编写单元测试**（使用 `t.TempDir()` 创建临时目录）：
   - 打开/关闭测试。
   - 单文件 CRUD 测试：Upsert → Get → Update → Get → Delete → Get。
   - UpsertIR 测试：全量写入 → 验证。
   - 持久化测试：关闭后重新打开，验证数据一致。
5. **SQLite 权威存储（已完成）**：基于纯 Go 的 `modernc.org/sqlite`（免 CGO）实现 `internal/store/sqlite`，完整实现 `store.Store` 接口（文件/类/方法/调用/标签 + 反向查询 + `UpsertIR` 增量入库）。`cmd/codeschema/main.go` 经 `newStore(cfg)` 接线，`storage.driver=sqlite` 即启用，默认仍 JSON 文件存储作 fallback。
6. **索引数据权限加固（已完成）**：落盘目录统一收紧为 0700、文件为 0600，由公共包 `internal/fsperm`（`MkdirAll`/`WriteFile`，显式 Chmod 覆盖 umask）提供；store 数据目录/`store.json`/锁文件、SQLite 目录、FTS、向量 JSON、IDF 均接入。详见 [安全设计文档](../跨圈层/安全设计文档.md)§7。

## 6. 并发扫描模型

```go
// Scanner 的并发模型设计：
//
// 1. 全量扫描：
//    - 使用 worker pool（默认 4 个 worker，可配置）
//    - 每个 worker 处理一个文件，调用 ProcessFile
//    - 每个 ProcessFile 使用独立事务
//    - 使用 semaphore 控制并发文件数，避免同时打开过多文件句柄
//
// 2. 增量监听：
//    - 单 goroutine 顺序处理 fsnotify 事件
//    - 防抖窗口内合并重复事件
//    - 每个事件触发 ProcessFile（独立事务）
//
// 3. 构建反向引用索引：
//    - 全量扫描时：单线程构建，避免并发写冲突
//    - 增量更新时：使用 sync.RWMutex 保护 reverse_import_cache
```
