# 12. 存储层扩展与大规模迁移路径

> 配套代码：`internal/scalebench`（超大仓基准）、`internal/store/pg`（PG 适配器骨架，`//go:build pg`）、`internal/store/redis`（Redis 缓存层骨架，`//go:build redis`）。
> 实测数据：`build/scale-bench.json`、`analysis/2026-08-14-scale-bench.md`。

## 12.1 现状

- 存储层统一接口 `internal/store.Store`，实现：`filestore`（JSON，默认 fallback）、`sqlitestore`（modernc.org/sqlite 纯 Go 免 CGO，已在 `storage.driver=sqlite` 启用）。
- 向量层 `internal/vector.ChromemStore` 封装 chromem-go（纯 Go）。
- **驱动分发缺口**：`store.NewStore` 当前仅分发 `"file"`；`cmd/codeschema/main.go` 的 `newStore(cfg)` 已单独接 sqlite。统一可插拔分发见 12.5。
- 本机实测已落地优化：`PRAGMA synchronous=NORMAL`（WAL，避免每事务 fsync），参见 `internal/store/sqlite/sqlite.go`。

## 12.2 超大仓瓶颈（基于实测，非理论推断）

基准合成每文件 1 类 / 3 方法 / 2 调用的归一化 IR，压测三类存储的「插入耗时 + 落盘耗时 + 内存」。数据已落盘 `build/scale-bench.json` 与 `analysis/2026-08-14-scale-bench.md`（本机杀软信任目录后成功写出）。

| N 文件 | FileStore Upsert(ms) | FileStore 落盘(ms) | FileStore 内存(MB) | SQLite 插入(ms) | SQLite 内存(MB) | chromem 插入(ms) | chromem 内存(MB) |
|---|---|---|---|---|---|---|---|
| 1,000 | 3.1 | 12.4 | 10.3 | 496.2 | 13.0 | 1.5 | 1.7 |
| 5,000 | 14.6 | 54.5 | 57.3 | 3556.3 | 65.4 | 9.2 | 8.5 |
| 10,000 | 33.9 | 105.3 | 114.7 | 6316.7 | 131.4 | 20.8 | 17.0 |
| 50,000 | 188.9 | 616.8 | 538.7 | 79229.4 | 657.5 | 101.2 | 84.6 |
| 100,000 | 354.4 | 17706.2 | 1078.7 | 180454.5 | 1355.9 | 181.4 | 169.3 |

> 重要说明（来源：本机 `go test ./internal/scalebench/` 实测，已落盘 `build/scale-bench.json`）：
> - **FileStore 落盘（Close 全量重写）列受 `t.TempDir()` 临时卷 I/O 主导，是环境噪声而非代码成本**：本机两次重跑该列在 @100k 分别测得 1.3s / 17.7s，剧烈波动且不随 N 稳定变化；在正常卷上其真实成本为 O(n) 单次（@100k 约 1~1.3s）。**请勿将该列读作序列化性能**。
> - **运行间绝对值有波动**（受本机负载 / GC / 临时卷影响）：SQLite 插入 100k 在 180~237s 间、FileStore Upsert 在 0.35~0.48s 间波动，但**趋势稳健**——FileStore/chromem 近似线性且快，SQLite 超线性且主导。
> - **内存列**为 `runtime.MemStats.TotalAlloc` 增量（含测试框架开销），仅作量级对比：FileStore 100k≈1.08GB、SQLite 100k≈1.36GB、chromem 100k≈169MB。
> - 单文件成本（@100k）：FileStore Upsert≈3.5µs、内存≈10.8KB；chromem Upsert≈1.8µs、内存≈1.7KB（含 384 维裸向量 1.5KB）；**SQLite≈1.8~2.4ms（最慢，约 500~1000× chromem）**。

结论（基于实测，推翻“FileStore O(n²) 写放大”的原假设）：

1. **SQLite（modernc 纯 Go 驱动）是超大仓写入的显性瓶颈**：10万文件单批插入 **180~237s（两次重跑区间）**，且超线性（每文件≈0.5ms@1k → ~1.8~2.4ms@100k）。根因：`UpsertIR` 对每个 IR 发多笔独立语句（file+class+3 method+2 call，~6 条/IR）且各事务独立，×纯 Go 驱动较慢。已落 `synchronous=NORMAL` 缓解；彻底解法见 12.5 的 **`BulkUpsert`（多文件/单事务批量）** 或切 PG / cgo-sqlite。
2. **FileStore 是纯内存存储**：`UpsertIR` 为 O(1) 摊还（@100k≈354ms，≈3.5µs/文件），真瓶颈是**内存 O(n)** ≈10.8KB/文件——100k≈1.1GB，1M≈11GB 将触顶；落盘为 `Close` 时一次性 O(n) 全量重写。适合中小仓 / 单仓原型，超大仓需分片或换落盘存储。
3. **chromem 扩展性最优**：插入线性（@100k≈181ms），内存线性（@100k≈169MB，远优于另两者）；向量数×dim×4 + 索引开销，百万级需 chromem 持久化(gob) + 分片或外置向量库。

## 12.3 PostgreSQL 迁移路径（`internal/store/pg`）

- 完整实现 `store.Store` 接口：事务化 `UpsertIR`、文件/类/方法/调用 CRUD、标签、反查、健康。
- 自带 PG 版 DDL（`SERIAL` 自增 + `now()` 默认值，对齐 `001_init.sql`）。
- 启用：

```bash
go get github.com/lib/pq
go build -tags pg ./...
# 配置 storage.driver=postgres, storage.dsn=postgres://user:pass@host:5432/codeschema?sslmode=disable
```

- 横向扩展收益：关系型引擎的并发写入、索引、分区表天然适配亿级文件；`call` 反查走 B-tree 索引。
- 注意：PG/Redis 适配器以 `//go:build pg` / `//go:build redis` 隔离，默认编译忽略（`go build ./...` 不受影响，无需改 go.mod）。`go.mod` 现已可写（本机已将仓库加入杀软信任目录），执行下方 `go get` 即可拉取驱动依赖并启用对应 build-tag 代码（骨架已就绪）。

## 12.4 Redis 缓存层（`internal/store/redis`）

- 热点类缓存（HASH）+ 调用反查索引（SET：`caller→callees` / `callee→callers`）+ 文件→类反向索引。
- 启用：

```bash
go get github.com/redis/go-redis/v9
go build -tags redis ./...
```

- 收益：高频「按 FQN 查类」「调用反查」走内存缓存，主存储（SQLite/PG）只承担持久化与全量检索。

## 12.5 推荐组合与启用步骤

1. **中小仓（<10万文件）**：FileStore（原型）/ SQLite（生产，已接）。
2. **大仓（10万~千万）**：SQLite 主存储 + chromem 持久化 + Redis 热点缓存；必要时 PG 接管关系型。
3. **亿级+**：PG 主存储 + Redis 缓存 + 分片向量库。
4. **统一驱动分发**：在 `store.NewStore` 补充 `sqlite`/`postgres`/`redis` 分支，让 `storage.driver` 一处切换（当前 main 已接 sqlite，待回填 NewStore 分发）。

## 12.6 已落地优化

- `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA busy_timeout=5000`：批量索引写入吞吐显著提升（每个 N 用独立 dsn 的实测对比见 `build/scale-bench.json`）。
- 超大仓基准框架 `internal/scalebench`：纯 Go、无 cgo，编译+运行分钟级，可重复压测。
