# 12. 存储层扩展与大规模迁移路径

> 配套代码：`internal/scalebench`（超大仓基准）、`internal/store/pg`（PG 适配器骨架，`//go:build pg`）、`internal/store/redis`（Redis 缓存层骨架，`//go:build redis`）。
> 实测数据：`build/scale-bench.json`、`analysis/2026-08-14-scale-bench.md`。

## 12.1 现状

- 存储层统一接口 `internal/store.Store`，实现：`filestore`（JSON，默认 fallback）、`sqlitestore`（modernc.org/sqlite 纯 Go 免 CGO，已在 `storage.driver=sqlite` 启用）。
- 向量层 `internal/vector.ChromemStore` 封装 chromem-go（纯 Go）。
- **统一分发已落地（2026-08-14）**：因 `sqlitestore`/`pg` 反向依赖 `internal/store`（实现其接口），`store.NewStore` 按设计仅分发 `"file"`，**不能**内联 sqlite/pg 分支（否则循环依赖）。实际分发落在 `cmd/codeschema` 层：`store_dispatch.go`（基础分发 + Redis 叠加点）、`store_pg.go`（`//go:build pg` 注册 PG）、`store_redis.go`（`//go:build redis` 叠加 Redis L2 缓存）。`storage.driver` 一处切换 file/sqlite/pg，Redis 由 `storage.kv` 单独控制。
- 本机实测已落地优化：`PRAGMA synchronous=NORMAL`（WAL，避免每事务 fsync），参见 `internal/store/sqlite/sqlite.go`。

## 12.2 超大仓瓶颈（基于实测，非理论推断）

基准合成每文件 1 类 / 3 方法 / 2 调用的归一化 IR，压测三类存储的「插入耗时 + 落盘耗时 + 内存」。数据已落盘 `build/scale-bench.json` 与 `analysis/2026-08-14-scale-bench.md`（本机杀软信任目录后成功写出）。

| N 文件 | FileStore Upsert(ms) | FileStore 落盘(ms) | FileStore 内存(MB) | SQLite(UpsertIR) 插入(ms) | SQLite 内存(MB) | SQLite(BulkUpsert) 插入(ms) | chromem 插入(ms) | chromem 内存(MB) |
|---|---|---|---|---|---|---|---|---|
| 1,000 | 4.1 | 9.9 | 10.3 | 422.6 | 13.0 | 51.9 | 2.1 | 1.7 |
| 5,000 | 14.0 | 47.0 | 57.3 | 2229.2 | 65.5 | 245.3 | 8.1 | 8.5 |
| 10,000 | 30.7 | 94.7 | 114.7 | 4857.1 | 131.4 | 854.8 | 24.5 | 17.0 |
| 50,000 | 179.2 | 568.6 | 538.7 | 24101.5 | 657.4 | 4518.3 | 72.2 | 84.6 |
| 100,000 | 405.6 | 1129.7 | 1078.7 | 114609.0 | 1311.8 | 13532.3 | 194.0 | 169.3 |

> 重要说明（来源：本机 `go test ./internal/scalebench/` 实测，已落盘 `build/scale-bench.json`）：
> - **FileStore 落盘（Close 全量重写）本机本次测得 @100k≈1.2s**，呈稳定 O(n)（与 N 同步增长），即真实序列化成本；早前测得的 17.7s 系 `t.TempDir()` 临时卷 I/O 噪声，已不再高估。
> - **运行间绝对值有波动**（受本机负载 / GC / WAL 检查点 fsync 抖动影响）：SQLite(UpsertIR) 插入 100k 在 77~237s 间波动，但**趋势稳健**——FileStore/chromem 近似线性且快，SQLite 超线性且主导。
> - **BulkUpsert 列**：将 100k 文件的整批灌入压为单事务 + 预编译语句，消除逐文件事务提交放大；实测 100k 由 UpsertIR 的上百秒级（本机波动 77~237s）降至 BulkUpsert 的约 5~14s（同样受负载波动），提速约一个数量级（跨 N 点位稳定 5~14× 提速），已生产可用。
> - **内存列**为 `runtime.MemStats.TotalAlloc` 增量（含测试框架开销），仅作量级对比：FileStore 100k≈1.08GB、SQLite 100k≈1.32GB、chromem 100k≈169MB。
> - 单文件成本（@100k）：FileStore Upsert≈3.3µs、内存≈10.8KB；chromem Upsert≈1.4µs、内存≈1.7KB（含 384 维裸向量 1.5KB）；**SQLite(UpsertIR)≈0.8ms（最慢，约 560× chromem）；SQLite(BulkUpsert)≈0.05~0.14ms（约 25~70× chromem，取 5~14s 区间）**。

结论（基于实测，推翻“FileStore O(n²) 写放大”的原假设）：

1. **SQLite（UpsertIR 逐文件路径）是超大仓写入的显性瓶颈**：10万文件单批插入 **77~237s（历史重跑区间，本机波动）**，且超线性（每文件≈0.8ms@100k）。根因：`UpsertIR` 对每个 IR 发多笔独立语句（file+class+3 method+2 call）且**每文件拆 4~5 事务**，100k 文件≈70万次事务提交放大 × 纯 Go 驱动较慢。已落 `synchronous=NORMAL` 缓解。
2. **FileStore 是纯内存存储**：`UpsertIR` 为 O(1) 摊还（@100k≈332ms，≈3.3µs/文件），真瓶颈是**内存 O(n)** ≈10.8KB/文件——100k≈1.1GB，1M≈11GB 将触顶；落盘为 `Close` 时一次性 O(n) 全量重写（@100k≈1.2s，稳定）。适合中小仓 / 单仓原型，超大仓需分片或换落盘存储。
   - **并发安全（2026-08-15 加固）**：FileStore 现持有进程级文件锁（Unix `flock` 排他 / Windows 独占创建，锁文件 `store.lock`），同一 store 目录被多进程（如 scan 与 serve 同时打开）并发写时，后者 Open 显式失败而非静默损坏 `store.json`；配合既有的「tmp 临时文件 + rename 原子替换」落盘，单进程内并发读写由 `sync.RWMutex` 保护。Scanner 同步忽略 `store.json`/`store.lock`/`store.db` 数据文件，避免 store 目录位于仓库根时被当作源码收录。
3. **chromem 扩展性最优**：插入线性（@100k≈138ms），内存线性（@100k≈169MB，远优于另两者）；向量数×dim×4 + 索引开销，百万级需 chromem 持久化(gob) + 分片或外置向量库。

### 12.2.1 真实全链路端到端压测（2026-08-15，T3-1）

> 与上文「存储层合成 IR 直插」不同，本数据走**完整生产路径**：真实 .go 文件落盘 → Scanner
> （tree-sitter 正则）→ UpsertIR(FileStore) → BuildFromStore → Searcher（内存 FTS + 向量）。
> 方法：`CODESCHEMA_SCALE_E2E_N=100000 go test -run TestScaleEndToEnd ./internal/scalebench/ -timeout 900s`；
> 报告 `build/scale-e2e.json` + `analysis/2026-08-15-scale-e2e.md`；CI nightly job 固化（N=10万 + 趋势 JSONL）。

| 指标 | N=1万 | N=10万 |
|---|---|---|
| 索引文档数 | 30,000 | 300,000 |
| 扫描耗时 | 657 ms | 8,176 ms（≈12.2k 文件/s） |
| 索引构建 | 592 ms | 9,553 ms |
| P95 搜索延迟 | 146.7 ms | 1,967 ms |
| 峰值堆内存 | 146.8 MB | 1,079 MB（≈10.8KB/文件） |

**规模决策表**：
- <1万 文件：默认栈 ✅（内存 <200MB、搜索 <50ms）；
- 1万~10万：⚠️ 默认栈内存 150MB~1.1GB、P95 146ms~2s → 上 SQLite（BulkUpsert）+ chromem 持久化向量；
- 10万~百万：🔴 默认栈内存触顶（1M≈11GB）→ **必须** PG 横向 + Redis 缓存 + chromem 持久化/分片；
- 百万+：PG 分区表 + 外置向量库（设计预留）。

**结论**：扫描/索引吞吐非瓶颈（10万≈18s 全链路）；瓶颈①默认栈内存 O(n)≈10.8KB/文件（已验证 10万≈1.1GB 触顶），
瓶颈②内存向量库在 30万 文档全量线性扫描下 P95 进入秒级——两者共同给出「>5万 切 SQLite、>10万 上 PG/Redis」的硬阈值。
4. **【已落地修复】BulkUpsert 消除事务提交放大**：`internal/store/sqlite.BulkUpsert`（单事务 + 预编译语句）将 100k 整批灌入由 UpsertIR 的上百秒级（本机波动 77~237s）压到 BulkUpsert 的约 5~14s（同样受负载波动），提速约一个数量级（跨 N 点位稳定 5~14×），生产化应使用它（analyzer 整仓重索引时批量灌入）。但 bulk 后 SQLite 仍比 chromem 慢约 40×（落盘 vs 纯内存），亿级仍建议走 PG。

## 12.3 PostgreSQL 迁移路径（`internal/store/pg`）

- 完整实现 `store.Store` 接口：事务化 `UpsertIR`、文件/类/方法/调用 CRUD、标签、反查、健康。
- 自带 PG 版 DDL（`SERIAL` 自增 + `now()` 默认值，对齐 `001_init.sql`）。
- 启用：

```bash
go get github.com/lib/pq
go build -tags pg ./...
# 配置 storage.driver=postgres, storage.dsn=postgres://user:pass@host:5432/codeschema?sslmode=disable
```

- 横向扩展收益：关系型引擎的并发写入、索引、分区表天然适配亿级文件；`call` 反查走 B-tree 索引。
- 注意：PG/Redis 适配器以 `//go:build pg` / `//go:build redis` 隔离，默认编译忽略（`go build ./...` 不受影响，无需改 go.mod）。`go.mod` 现已可写（本机已将仓库加入杀软信任目录），执行下方 `go get` 即可拉取驱动依赖并启用对应 build-tag 代码（骨架已就绪）。

## 12.4 Redis 缓存层（`internal/store/redis`）

- 热点类缓存（HASH）+ 调用反查索引（SET：`caller→callees` / `callee→callers`）+ 文件→类反向索引。
- 启用：

```bash
go get github.com/redis/go-redis/v9
go build -tags redis ./...
```

- 收益：高频「按 FQN 查类」「调用反查」走内存缓存，主存储（SQLite/PG）只承担持久化与全量检索。

## 12.5 推荐组合与启用步骤

1. **中小仓（<10万文件）**：FileStore（原型）/ SQLite（生产，已接）。
2. **大仓（10万~千万）**：SQLite 主存储 + chromem 持久化 + Redis 热点缓存；必要时 PG 接管关系型。
3. **亿级+**：PG 主存储 + Redis 缓存 + 分片向量库。
4. **统一驱动分发（已落地）**：分发位于 `cmd/codeschema`（`store_dispatch.go` + `store_pg.go` + `store_redis.go`，均 build-tagged 隔离），而非 `internal/store.NewStore`——后者因循环依赖只能保留 `file` 分支。`storage.driver` 一处切换 file/sqlite/pg；Redis 作为可选 L2 缓存层由 `storage.kv` 控制，地址为空即不启用（优雅降级回基础存储）。

## 12.6 已落地优化

- `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA busy_timeout=5000`：批量索引写入吞吐显著提升（每个 N 用独立 dsn 的实测对比见 `build/scale-bench.json`）。
- 超大仓基准框架 `internal/scalebench`：纯 Go、无 cgo，编译+运行分钟级，可重复压测；新增 `benchSQLiteBulk` 对比 `BulkUpsert` vs `UpsertIR`。
- **`BulkUpsert` 回归看护已固化进 CI**：`.github/workflows/ci.yml` 新增 `bench` job，跑 `go test -run '^$' -bench=BenchmarkScaleBulk ./internal/scalebench`（N=1万、秒级）守护单事务批量入库成本，防止「逐文件事务提交放大」回潮；注意同包 `TestScaleBench` 为全量 N=1k~100k 慢测试（分钟级），CI 用 `-run '^$'` 仅跑基准、不触发它。
- `BulkUpsert`（单事务 + 预编译语句）：`internal/store/sqlite.BulkUpsert` 消除逐文件事务提交放大，100k 落库从 77~237s 降至约 5~14s（约一个数量级 / 跨 N 点位稳定 5~14× 提速）；`filestore`/`pg` 同步实现接口方法，`analyzer` mock 补齐（另含 `internal/ai`、`internal/service` 两处测试 mock 补齐）。
