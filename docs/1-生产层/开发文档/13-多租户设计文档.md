# 13 - 多租户（单实例多仓库）

> **开发顺序**：横跨所有阶段，属于「部署形态」增强
>
> **前置依赖**：[00-项目概述与架构概览.md](00-项目概述与架构概览.md)、[11-配置部署与路线图.md](11-配置部署与路线图.md)

当一个团队里有多个项目（仓库）都需要 CodeSchema 时，有三种典型思路：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 多实例 | 每个项目各起一个 `codeschema` 进程，各自绑定不同端口/配置 | 隔离彻底、零改动 | 进程数随项目线性增长，运维/资源成本高，端口与配置难以管理 |
| B. 单实例多租户（**本方案**） | 一个进程持有 N 个隔离的单租户运行实例，按 `project` 路由 | 运维简单、资源复用、统一接入 | 单进程是瓶颈（但本系统存储/检索为零依赖本地引擎，瓶颈在 IO/内存，可接受） |
| C. 单库多项目 | 一个 store，记录里带 `tenant` 列 | 最简单 | 需改造 `Store` 接口，且破坏「单租户 Store 与 pg/redis 后端在 cmd 层按 build tag 分发」的循环依赖隔离约束 |

**结论**：采用 **B 方案**——单实例 + 多份隔离的单租户运行实例，存储隔离通过「每租户独立 store」实现，不修改 `internal/store.Store` 接口，因此既支持 `file/sqlite`，也天然兼容 `-tags pg/redis` 后端。

---

## 1. 架构设计

```
                    ┌──────────────────────────────────────────┐
   AI Agent ───────▶│           单实例 CodeSchema 进程           │
                    │                                            │
   HTTP :18099  ───▶│  server.HTTPServer / server.MCPServer      │
   MCP  :18098  ───▶│        │  resolveTenant(project)          │
                    │        ▼                                   │
                    │   tenant.Manager                          │
                    │   ┌─────────┐  ┌─────────┐  ┌─────────┐   │
                    │   │ demo-a  │  │ demo-b  │  │  ...    │   │
                    │   │ store   │  │ store   │  │ store   │   │
                    │   │ runtime │  │ runtime │  │ runtime │   │
                    │   │ Service │  │ Service │  │ Service │   │
                    │   │ index   │  │ index   │  │ index   │   │
                    │   └────┬────┘  └────┬────┘  └────┬────┘   │
                    └────────┼────────────┼────────────┼───────┘
                             ▼            ▼            ▼
                         ./build/mt-a  ./build/mt-b  ...（各自独立目录）
```

- `tenant.Manager` 持有一组 `Tenant`，每个 `Tenant` 是一个完整的**单租户运行实例**：独立的 `store.Store` + 独立 `runtime.Runtime`（`Service` + `Searcher` + 索引）。
- 请求到达时，按 `project` 标识路由到对应 `Tenant.Service`，其余代码路径与单项目模式完全一致。
- `openStore` 工厂由 `cmd` 层注入（`tenant.OpenStoreFunc`），使 `tenant` 包不依赖 build-tagged 的 pg/redis 分发逻辑，维持 `internal/store` 的循环依赖隔离。

---

## 2. 隔离边界（关键）

多租户的正确性**不依赖**「在记录里加 tenant 列」，而是依赖**每个租户拥有完全独立的物理存储**：

| 资源 | 隔离方式 | 说明 |
|---|---|---|
| 主存储（实体/调用关系/标签） | 每租户独立 `store`（DSN 不同） | `file` → 不同目录；`sqlite` → 不同文件；`pg` → 由用户用不同连接串/schema 区分 |
| 全文索引 FTS | 每租户独立 `search.fts_dir` | **默认按 store 目录派生为 `<dsn>/fts`** |
| 向量索引 | 每租户独立 `search.vector_dir` | 默认 `<dsn>/vector` |
| IDF 词典 | 每租户独立 `search.idf_dir` | 默认 `<dsn>/idf` |

> ⚠️ **踩坑记录**：早期实现只隔离了主 `store` 的 DSN，但 FTS/向量/IDF 目录仍沿用 `DefaultConfig` 的 `./data/fts` 等**共享默认值**。由于多租户按注册顺序依次 `auto_scan`，后扫描的租户会**覆盖共享索引**，导致所有租户都返回最后一个租户的数据。修复方式：对显式 `tenants`，在其**未显式配置**检索/向量目录时，自动按各自 store 目录派生隔离子目录（仅对目录型后端 `file/sqlite` 生效；`pg` 等由用户显式配置）。

索引目录派生规则（`internal/tenant/tenant.go` 的 `deriveIndexDirs`）：

```go
// 仅当租户原始配置未显式设置对应目录时，按 store 目录派生
switch driver {
case "file", "sqlite", "":
    if tenantCfg.Search.FTSDir    == "" { FTSDir    = filepath.Join(dsn, "fts") }
    if tenantCfg.Search.VectorDir == "" { VectorDir = filepath.Join(dsn, "vector") }
    if tenantCfg.Search.IDFDir    == "" { IDFDir    = filepath.Join(dsn, "idf") }
}
```

## 3. 配置模型

在根配置中新增 `tenants` 列表。每一项是一个**单租户覆盖层**，通过 `TenantConfig.ToConfig(base)` 克隆全局配置并叠加租户显式设置的字段（storage/vector/search/parser/ai/watcher/scanner 等）。

```yaml
# build/mt-demo.yaml（可运行示例，见仓库 build/mt-demo.yaml）
server:
  http_addr: ":18099"
  mcp_addr: ":18098"

tenants:
  - id: demo-a                       # 租户 ID，路由键（project 参数 / X-Tenant / ?tenant=）
    name: Demo A                     # 展示名（list_projects 返回）
    root: ./cmd                      # 该仓库根路径（auto_scan / watch 目标）
    storage:
      driver: file
      dsn: ./build/mt-a              # 该租户独立存储目录（索引自动派生到其下）
    auto_scan: true                  # 启动时全量扫描
  - id: demo-b
    name: Demo B
    root: ./internal/config
    storage:
      driver: file
      dsn: ./build/mt-b
    auto_scan: true
```

**叠加规则**：租户仅覆盖写明的字段；未写明的继承全局 `base` 配置。因此你可以把 vector/ai/watcher 等公共配置放在根级，租户只写 `id/name/root/storage.dsn/auto_scan` 等差异项。

**校验**（`config.Validate`）：每个租户 `id` 非空且唯一；`storage.dsn` 非空（为空时自动补 `./data/<id>`，但建议显式写明以避免误共享）。

## 4. 路由规则

请求通过以下任一方式指定目标租户，**缺省则使用默认租户**（注册表中的第一个，单项目模式下为 `"default"`）：

| 传输 | 指定方式 | 示例 |
|---|---|---|
| MCP 工具调用 | 工具参数 `project`（所有 12 个工具均支持） | `search_symbols({ q: "Config", project: "demo-a" })` |
| HTTP API | 请求头 `X-Tenant` 或查询参数 `?tenant=` | `GET /search?q=Config&tenant=demo-a` |
| 默认 | 不指定 | 路由到默认租户 |

`list_projects` 工具 / `GET /projects` 端点返回当前实例服务的全部租户元信息（`id / name / root`），便于客户端发现可用仓库。

## 5. 使用方式

### 5.1 启动（serve / mcp 共用同一份 --config）

```bash
# 单实例同时服务 demo-a 与 demo-b
./codeschema --config build/mt-demo.yaml serve     # HTTP :18099 + 可视化
./codeschema --config build/mt-demo.yaml mcp       # MCP SSE :18098
```

> 注意：全局 `--config` 必须放在子命令**之前**：`./codeschema --config X serve`。

### 5.2 HTTP 示例

```bash
curl localhost:18099/projects
# {"default":"demo-a","projects":[{"id":"demo-a","name":"Demo A","root":"./cmd"},
#                                 {"id":"demo-b","name":"Demo B","root":"./internal/config"}]}

curl "localhost:18099/search?q=Config&tenant=demo-a"   # 仅返回 cmd/ 结果
curl "localhost:18099/search?q=Config&tenant=demo-b"   # 仅返回 internal/config/ 结果
```

### 5.3 MCP 示例（JSON-RPC over SSE /message）

```json
{ "jsonrpc": "2.0", "id": 1, "method": "tools/call",
  "params": { "name": "search_symbols",
              "arguments": { "q": "Config", "project": "demo-a" } } }
```

## 6. 向后兼容

- **无 `tenants` 配置**时，`Manager` 自动构造单个隐式租户 `"default"`（沿用全局配置），所有接口行为与此前完全一致——`project` 参数可省略，`/projects` 与 `list_projects` 仅返回 `default`。
- 单项目模式的 CLI（`scan` / `watch`）未改动，仍走 `internal/runtime` 直接装配，不经过 `Manager`。

## 7. Docker Compose 多租户

在 compose 中使用一份带 `tenants` 的配置文件即可。相比单租户，只需：

1. 准备 `config.mt.yaml`，写入 `tenants:` 块（每个租户挂载各自的仓库目录与存储目录）；
2. `command` 改为 `["serve", "--config", "/app/config.mt.yaml"]`；
3. 为各租户仓库分别挂载卷（只读）。

可运行的最小示例见仓库 `build/mt-demo.yaml`；compose 片段参考 [11-配置部署与路线图.md](11-配置部署与路线图.md) 第 8 节。

## 8. 已知限制与路线图

- **单进程瓶颈**：所有租户共享一个进程的 CPU/内存。当前零依赖本地引擎下可接受；超大集群可退化为方案 A（按项目组拆分多实例）。
- **pg 后端隔离**：`file/sqlite` 自动按目录隔离索引；`pg` 租户需由用户用不同连接串/schema 区分，且应显式配置 `search.fts_dir/vector_dir/idf_dir`（不要依赖默认 `./data/*`）。
- **热重载**：当前 `tenants` 在进程启动时固定，修改后需重启；后续可在 P9 配置热重载中支持租户增减（动态 `buildTenant` / `Close`）。

## 9. 验证记录（smoke test）

实现后已用 `build/mt-demo.yaml`（demo-a→`./cmd`，demo-b→`./internal/config`）端到端验证：

- `GET /projects` 正确返回两个租户；
- HTTP `?tenant=demo-a` 仅返回 `cmd/codeschema/*`，`?tenant=demo-b` 仅返回 `internal/config/*`；
- MCP `list_projects` 返回两个租户；`search_symbols({project:"demo-a"})` 仅返回 `cmd/`，`{project:"demo-b"}` 仅返回 `internal/config/`；
- 默认租户（省略 `project`）正确回退到 `demo-a`（注册表首项目）。

构建与测试：`go build ./...`、`go build -tags pg,redis ./...`、`go vet ./...` 均通过；`internal/server`、`internal/config` 测试通过（MCP 工具数断言已更新为 12）。
