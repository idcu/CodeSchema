## 1. 完整配置模型

```yaml
# config.yaml — 完整配置项
project:
  name: myrepo                    # 项目名称
  root: ./repo                    # 仓库根路径
  languages: [go, java, cpp, ts]  # 目标语言列表

storage:
  driver: file                    # file（默认，JSON 零依赖）| sqlite | pg/postgres（需 -tags pg）
  dsn: ./data                     # 数据目录/数据库连接串
  kv: redis://localhost:6379/0    # Redis L2 缓存（需 -tags redis；空则不启用）
  vector:
    driver: chromem               # 可选后端：仅显式=chromem 时启用（否则默认文件 PersistentStore）；默认留空即文件后端
    dsn: ./vector.db              # 向量库路径/连接串（chromem 持久化文件；默认空→VectorDir/chromem.db）
    embedding_model: bge-small-zh-v1.5
    model_dir: ./down/models/bge-small-zh-v1.5
    model_download_url: ""        # ONNX 模型远程分发（{model} 占位）
    model_sha256: ""              # 模型包 SHA-256 校验和
    embedding_model: bge-small-zh-v1.5 # Embedding 模型
  search:
    fts: true                     # 启用全文搜索（PersistentFTS，纯 Go）
    semantic: true                # P2 启用，语义检索

parser:
  adapters: [scip, treesitter, codegraph, jcodeindexer]  # 启用的适配器列表
  scip:
    index_dir: ./scipout          # SCIP index 输出目录
  codegraph:
    db: ./codegraph.db            # CodeGraph SQLite 路径
  jcodeindexer:
    db: ./jcodeindexer.db         # JCodeIndexer SQLite 路径
    config_file: .jindexer/config.yaml  # 兼容 JCI 配置约定
    env:
      INDEXER_EMBEDDING_ENABLED: "false"

ai:
  provider: openai                # OpenAI 兼容客户端（BaseURL 可指向任意兼容端点）
  base_url: https://api.openai.com/v1   # API 根地址；空则禁用 AI
  api_key: ""                     # 鉴权密钥；空则禁用 AI
  model: gpt-4o-mini              # LLM 模型名
  budget_per_scan: 100            # 每次扫描 AI 调用硬限
  budget_per_query: 10            # 每次查询 AI 调用硬限

server:
  mcp_addr: ":8080"               # MCP Server 监听地址
  http_addr: ":8081"              # HTTP API 监听地址
  auth_token: ""                  # 空字符串表示不启用认证
  rate_limit: 0                   # 全局限流：每分钟请求上限（令牌桶）；0=不限流（默认）

watcher:
  enabled: true                   # 是否启用文件监听
  debounce_ms: 300                # 防抖窗口（毫秒）
  ignore_dirs: [".git", "node_modules", "target", "build"]  # 忽略的目录
  batch_size: 50                  # 单批处理的最大文件数

scanner:
  workers: 4                      # 并发解析 worker 数
  file_size_limit_mb: 10          # 超过此大小的文件标记为 parse_skipped
  line_count_limit: 50000         # 超过此行数的文件标记为 parse_skipped
```

## 5. 实测对标方案

### 5.1 步骤

1. **仓库选取**：7 个真实开源仓库（覆盖 Go/Java/TypeScript，规模 1k–50k 文件），与 CodeGraph benchmark 仓库尽量重叠。
2. **指标采集**：每次问答采集 `prompt_token`、`completion_token`、`tool_call_count`、`latency_ms`；分别统计有/无本系统裁剪两组。
3. **口径**：`token_saving = 1 - tokens_with_system / tokens_without_system`（median，跨 7 仓库）；`tool_call_reduction`、`cost_reduction` 同口径。
4. **输出**：使用已落地的 `codeschema benchmark ./repo` 子命令生成报告（markdown + csv）——当前 CLI 7 命令（scan/watch/rebuild-kv/benchmark/mcp/serve/version），benchmark 已实现；含每仓库原始值与 7 仓库 median，与 CodeGraph 数据并列呈现。
5. **门槛**：若实测 `token_saving_median < 90%`，触发检索/裁剪策略复盘（先查召回率，再调裁剪窗口）。

## 6. 风险识别与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 单维护者风险外溢（CodeGraph 约 91% 单人维护） | CodeGraph 停更 → 直读适配器失效 | 直读适配器始终保留 tree-sitter/SCIP 降级路径；P3 健壮性测试覆盖 |
| 工作量低估 | P0 排期失控 | 工期修正为 5-7 周；骨架（2 周）与可用 MVP（3-5 周）拆为两个里程碑 |
| 实测数据缺失 | token 节省仅为理论值 | P1 完成 7 仓库 benchmark，出 median 报告 |
| MCP 互操作未对齐 | Agent 接入需适配，迁移成本高 | 工具命名/语义对齐 CodeGraph + JCodeIndexer 事实标准 |
| 语义检索已落地（历史风险已解除） | 模糊/跨文件语义查询已具备 | chromem-go + bge-small-zh-v1.5 向量 + FTS5 双路已落地（P6/P6_2，Recall@1=1.00） |
| 许可证合规 | 内嵌竞品代码引发合规风险 | 仅消费产出或子进程调用 LSP，不内嵌任何竞品代码 |
| 大文件/生成文件污染索引 | 索引膨胀、AI 整文件读取超时 | `byte_size`/`line_count` 阈值旁路；`parse_status='parse_skipped'` 留痕 |
| 行号跨版本漂移 | rename/move 后实体匹配失败 | 区间重叠 + 全限定名兜底；git diff 行号平移辅助；主键不依赖行号 |
| 跨文件反向引用增量性能 | 每次文件变更触发全量扫描 | 局部反向引用重算 + 延迟批量重建策略 |

## 7. P9 配置热重载 / 多配置源支持

### 7.1 环境变量覆盖

P9 新增 `LoadFromEnv` 函数，支持从环境变量加载配置覆盖。环境变量按 `CODESCHEMA_<SECTION>_<KEY>` 命名规则（全大写，下划线分隔）：

```bash
# 示例
CODESCHEMA_PROJECT_ROOT="/home/user/repo"
CODESCHEMA_STORAGE_DRIVER="sqlite"
CODESCHEMA_SERVER_MCP_ADDR=":9090"
CODESCHEMA_SCANNER_WORKERS="8"
CODESCHEMA_WATCHER_DEBOUNCE_MS="500"
CODESCHEMA_AI_BUDGET_PER_SCAN="200"
CODESCHEMA_WATCHER_ENABLED="false"
```

**优先级**：默认值 < 配置文件 < 环境变量 < CLI 参数

### 7.2 配置合并 (Merge)

`Merge(base, overlay *Config) *Config` 函数合并两个配置实例，返回新实例，不修改原始实例。

合并策略：

| 类型 | 策略 |
|------|------|
| 字符串 | overlay 非空则覆盖 |
| 整型 | overlay > 0 则覆盖 |
| 布尔型 | overlay 为 true 则覆盖（零值 false 不覆盖） |
| 切片 | overlay 非空则覆盖 |
| map | overlay 非空则覆盖 |

### 7.3 配置热重载 (ConfigWatcher)

`ConfigWatcher` 使用轮询方式检测配置文件变更（默认 2 秒间隔），自动重新加载并原子切换配置。

```go
cw := config.NewConfigWatcher("/path/to/config.yaml", cfg, func(oldCfg, newCfg *config.Config) {
    log.Printf("config reloaded: watcher.debounce_ms %d → %d",
        oldCfg.Watcher.DebounceMs, newCfg.Watcher.DebounceMs)
})
go cw.Start(ctx)
defer cw.Stop()

// 后续使用 cw.GetConfig() 获取最新配置
```

**线程安全**：`GetConfig()` 通过 RWMutex 保护，读取无阻塞。回调注册使用 `SetOnReload(fn)`（线程安全，可在 `Start` 前后任意时刻调用，传 nil 取消）。

**注意**：配置热重载仅更新 Config 实例本身，不自动重新初始化依赖该配置的服务。需通过 `OnReload` 回调手动处理服务重初始化（如调整 Scanner workers 数量、更换 Store DSN 等）。**已落地示例**：
- serve / mcp 命令通过 `SetOnReload` 联动 `tenant.Manager.Apply`，实现多租户集合的增量热重载（新增/移除/关键字段变更无需重启进程），见 [13-多租户设计文档.md](13-多租户设计文档.md) §5.4。
- 服务级配置热重载：`tenant.Manager.Apply` 的变更判定（`tenantDirty`）覆盖 `scanner.workers` / `scanner.file_size_limit_mb` / `scanner.line_count_limit`，与 DSN/Root/Name/autoScan/watch 一并触发租户实例重建（Commit 121）。
- 全局能力热重载：serve 命令联动 `HTTPServer.UpdateRuntime`，配置变更时**无需重启进程**即时生效 ① 认证令牌（`server.auth_token`）② 全局限流（`server.rate_limit`，0 关闭）③ 监听地址（`server.http_addr`，无中断重绑：新监听立即接管、旧监听关闭、在途请求由原 server 处理完毕）；mcp 命令联动 `MCPServer.SetAuthToken` 即时更新 `server.auth_token`。`preset` 变更经 `config.Load` 重新应用，其影响的服务端字段在此连带生效。

## 9. 多租户（单实例多仓库）

多个项目都需要 CodeSchema 时，**推荐单实例多租户**：一个进程持有若干个隔离的单租户运行实例（各自独立 store + 独立检索/向量索引），按 `project` 路由，无需为每个项目各起一个进程。完整设计与验证见 [13-多租户设计文档.md](13-多租户设计文档.md)。

### 9.1 配置（tenants 覆盖层）

在根配置新增 `tenants` 列表。每个租户仅覆盖差异字段（其余继承全局），**务必为每个租户指定独立的 `storage.dsn`**：

```yaml
server:
  http_addr: ":18099"
  mcp_addr: ":18098"
tenants:
  - id: demo-a
    name: Demo A
    root: ./cmd
    storage: { driver: file, dsn: ./build/mt-a }
    auto_scan: true
  - id: demo-b
    name: Demo B
    root: ./internal/config
    storage: { driver: file, dsn: ./build/mt-b }
    auto_scan: true
```

> ⚠️ **索引隔离**：全文（FTS）/向量/IDF 索引目录默认按各自 `storage.dsn` 目录派生为 `<dsn>/fts`、`/<dsn>/vector`、`/<dsn>/idf`。**不要**让多个租户共用同一 `dsn` 或默认 `./data/*` 索引目录，否则后扫描者会覆盖前者索引。显式设置 `storage.search.fts_dir/vector_dir/idf_dir` 可覆盖默认派生。

### 9.2 启动与路由

```bash
./codeschema --config build/mt-demo.yaml serve   # HTTP :18099
./codeschema --config build/mt-demo.yaml mcp      # MCP SSE :18098
```

- HTTP：`GET /projects` 枚举租户；`X-Tenant` 头或 `?tenant=` 指定目标租户。
- MCP：所有 12 个工具支持 `project` 参数；`list_projects` 枚举租户。
- 缺省（不指定）→ 默认租户（注册表首个；无 `tenants` 时为 `"default"`，行为同单项目模式）。
- **热重载**：`--config` 模式自动启用配置文件轮询，`tenants` 列表变更（新增/移除/关键字段修改）自动增量更新租户集合，**无需重启进程**。不改动的租户保持原实例，不会打断在途请求。
- **全局能力热重载**：同一配置文件变更还会即时生效 ① 认证令牌 ② 全局限流 ③ HTTP 监听地址（无中断重绑），详见 §7.3。

### 9.3 Docker Compose 多租户

复用同一镜像，挂载一份带 `tenants:` 的配置文件，并为各租户仓库分别挂载卷（只读）。最小可运行示例见仓库 `build/mt-demo.yaml`。关键差异：

```yaml
services:
  codeschema-mt:
    image: codeschema:latest
    volumes:
      - codeschema-mt-data:/app/data
      - ${REPO_A}:/repo-a:ro
      - ${REPO_B}:/repo-b:ro
      - ${MT_CONFIG}:/app/config.mt.yaml:ro
    command: ["serve", "--config", "/app/config.mt.yaml"]
# config.mt.yaml 中 tenants[0].root=/repo-a、tenants[1].root=/repo-b，
# 各自 storage.dsn 指向 /app/data/mt-a、/app/data/mt-b
```

## 9. P13 构建与部署指南

### 9.1 构建脚本（Makefile）

项目根目录 `Makefile` 提供以下构建目标：

| 目标 | 说明 | 使用场景 |
|------|------|---------|
| `build` | 当前平台构建（CGO_ENABLED=0） | 快速构建纯 Go 二进制 |
| `build-cgo` | 启用 CGO 构建（须有 GCC） | 本地调试，含 SQLite/tree-sitter |
| `test` | 运行全部测试 | 提交前验证 |
| `test-race` | 竞态检测 | CI 流程 |
| `test-cover` | 覆盖率报告 | 质量门禁 |
| `bench` | 性能基准测试（BenchmarkScaleBulk/Concurrent/SQLiteWALConfigs） | 性能评估 |
| `bench-callgraph` | 调用图精度基准 | 精度门槛 |
| `bench-trend` | 基准趋势对比 | 跨提交回归 |
| `models-pack` | 打包 ONNX 模型制品（tar.gz + sha256） | 离线分发 |
| `models-serve` | 本地 HTTP 分发模型制品 | 离线/内网安装 |
| `lint` | go vet 代码检查 | 代码质量 |
| `cross` | 交叉编译（5 平台） | 发布多平台二进制 |
| `clean` | 清理构建产物 | 恢复初始状态 |
| `run` | 构建并运行 | 本地调试 |

```

codeschema-darwin-amd64
codeschema-darwin-arm64
```

### 9.2 Docker 容器化

**Dockerfile** 采用多阶段构建：

```
golang:1.25-alpine (builder) → alpine:3.20 (runtime)
```

构建命令：

```bash
# 构建镜像：默认即启用 ONNX 语义检索（CGO_ENABLED=1 + -tags onnx），
# 通过 go mod vendor 离线构建（vendor/ 随构建上下文提供），不依赖 gitee 发布状态
# （含未发版的 gitee.com/idcu-go/recovery、trace 等本地 replace 模块）。
# 纯 Go 免 CGO 镜像可传 --build-arg CGO_ENABLED=0（语义检索降级 LocalEmbedder）。
# Go 模块代理默认 goproxy.cn（国内网络可复现构建），可 --build-arg 覆盖。
docker build -t codeschema:latest --build-arg VERSION=$(git describe --tags) .

# 运行（默认启动 HTTP API）
docker run -p 8081:8081 \
  -v ./data:/app/data \
  codeschema:latest

# 指定配置文件运行（多租户：挂载带 tenants: 的配置 + 各租户仓库卷）
docker run -p 8080:8080 -p 8081:8081 \
  -v ./config.yaml:/app/config.yaml:ro \
  -v ./data:/app/data \
  codeschema:latest --config /app/config.yaml mcp --addr :8080
```

> **镜像 ONNX 默认开启，与本地 `make build` 不同**：Docker 镜像默认 `CGO_ENABLED=1 -tags onnx`（语义检索用真实 ONNX 模型 `bge-small-zh-v1.5`，dim=512）；本地 `make build` 默认 `CGO_ENABLED=0` 纯 Go（语义检索降级 LocalEmbedder）。二者结构化 / FTS / 影响面分析能力一致。
>
> **基础镜像必须用 glibc（Debian bookworm），不能用 alpine/musl**：onnxruntime 预编译的 `libonnxruntime.so` 依赖 `libstdc++.so.6` / `libgomp` 等 glibc 运行时，musl 无法加载该 `.so`，会导致 ONNX 静默降级为 LocalEmbedder（日志出现 `ONNX embedder not loaded ... → using LocalEmbedder`）。运行阶段已安装 `libstdc++6 libgomp1`。若自行改基础镜像，务必选 glibc 系并补齐这两个库。

**依赖解析策略（2026-09-01 修正）**：原 Dockerfile 在构建期 `go mod edit -dropreplace` 去掉 `../idcu-go/*` 本地 replace、改从 gitee 拉发布版。但该假设不成立——`gitee.com/idcu-go/recovery` 与 `trace` 从未发布到 gitee，去掉 replace 后 `go mod download` 直接报 `unknown revision`。现改为 `go mod vendor`：把 go.mod 中全部本地 replace（含 recovery/trace、down/chromem-go、third_party/onnxruntime_go_patch）固化进 `vendor/`，Docker 以 `-mod=vendor` 离线构建，代码与本地开发一致、且不依赖 gitee 可用性。修改 go.mod 后须重跑 `go mod vendor` 保持 `vendor/modules.txt` 同步。

#### onnxruntime 运行时库获取方式（跨平台）

`onnxruntime_go` 编译时只依赖 CGO，但运行时需要对应平台的原生动态库：

| 平台 | 动态库文件名 | 下载包名（版本） |
|------|-------------|---------|
| Windows | `onnxruntime.dll` | `onnxruntime-win-x64-1.28.0.zip` |
| Linux | `libonnxruntime.so` | `onnxruntime-linux-x64-1.28.0.tgz` |
| macOS (Apple Silicon) | `libonnxruntime.dylib` | `onnxruntime-osx-arm64-1.28.0.tgz` |
| macOS (Intel，x86_64) | `libonnxruntime.dylib` | `onnxruntime-osx-x86_64-1.23.2.tgz` |

**下载**：从 [ONNX Runtime Releases](https://github.com/microsoft/onnxruntime/releases) 下载对应平台的预编译包。

> **macOS Intel 注意（版本锁定）**：ONNX Runtime 上游 **自 1.23.2 后不再发布 macOS x86_64 版本**（仅保留 Apple Silicon arm64 更新）。因此 macOS Intel(x86_64) 只能使用 `onnxruntime-osx-x86_64-1.23.2.tgz`，并依赖 `third_party/onnxruntime_go_patch`（`ORT_API_VERSION 23`）适配；新机器请使用 Apple Silicon（arm64）1.28.0。

**放置路径**：

| 平台 | 推荐路径 | 构建方式 |
|------|---------|---------|
| Windows | `down/onnxruntime/onnxruntime.dll` | `make build-cgo` 自动复制到输出目录 |
| Linux | `down/onnxruntime/libonnxruntime.so` | `make build-cgo` 自动复制到输出目录 |
| macOS | `down/onnxruntime/libonnxruntime.dylib` | `make build-cgo` 自动复制到输出目录 |

也可将动态库放到系统库搜索路径（Linux: `LD_LIBRARY_PATH`，macOS: `DYLD_LIBRARY_PATH`，Windows: `PATH`）或程序运行同目录。

**bge-small-zh-v1.5 模型获取**：模型已预转换为 ONNX 格式（FP16 量化），从 [bge-small-zh-v1.5 ONNX 版本](https://huggingface.co/BAAI/bge-small-zh-v1.5/tree/main/onnx) 下载：

| 文件 | 说明 |
|------|------|
| `model_fp16.onnx` | FP16 量化模型图（~42KB） |
| `model_fp16.onnx_data` | FP16 模型权重（~47MB） |
| `tokenizer.json` | WordPiece 分词器（~362KB） |
| `config.json` | 模型配置 |

放置到 `down/models/bge-small-zh-v1.5/` 目录下：

```
down/models/bge-small-zh-v1.5/
├── config.json
├── tokenizer.json
└── onnx/
    ├── model_fp16.onnx
    └── model_fp16.onnx_data
```

**Docker 部署**：如需在容器内使用 ONNX 加速，需在 Dockerfile 运行时阶段安装对应平台的 `libonnxruntime.so`，参见 [Dockerfile](#92-docker-容器化) 中的注释说明。

**注意**：语义检索支持 ONNX 模型嵌入加速。`bge-small-zh-v1.5` 模型已预转换为 ONNX 格式（FP16 量化），位于 `down/models/bge-small-zh-v1.5/`。应用启动时自动检测 ONNX 模型，优先使用 `ONNXEmbedder`，失败时降级到 `LocalEmbedder`（TF-IDF 哈希）。
