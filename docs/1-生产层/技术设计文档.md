## 1. 系统定位

**CodeSchema** 是面向 AI 辅助开发的**代码元数据索引与上下文裁剪服务**：把仓库中的类、方法、接口、继承关系、调用关系、文件路径/行号/参数/返回值/用途标签等沉淀为「文件存储（权威源）+ 内存索引（热读）+ 向量索引（语义检索）」三层存储，通过 MCP Server 向 AI Agent 供给**精准裁剪后的代码上下文**（大幅节省 token、改一行反查影响面、只跑相关单测）。

**非目标**：不自研多语言 AST/类型系统/语义分析（解析外包 tree-sitter/LSP/SCIP/竞品产出）；不做通用搜索引擎；AI 只做校验/补全/兜底，不承担主解析。

## 2. 五层架构

```
接入层：CLI · HTTP API · MCP Server（12 工具，含 list_projects）
编排层：Scanner · Scheduler · Watcher（轮询默认 / fsnotify 可选）· 事务
解析适配中间层（核心）：tree-sitter(通用兜底) · SCIP(精确语义) · LSP(校正) · 竞品直读(CodeGraph)
                        └ 统一 IRDocument（ParserPlugin 接口契约）
AI 增强层（按需 · 预算硬限）：Tagger · DocEnhancer · RiskMarker · Disambiguator
存储层：file(默认) / SQLite / PostgreSQL / Redis(KV热读) + 向量索引 + 全文检索(PersistentFTS)
```

**模块耦合规则**：
- 解析中间层除统一 IR 定义外不依赖任何具体解析器；各适配器独立子包，可单独编译/测试/启停。
- AI 增强层对 IR 操作，不直接调用解析器。
- 竞品直读适配器在源不可用时**自动降级**到 tree-sitter/SCIP/LSP。
- 新增语言 = 新增一个 adapter 子包 + `Register()`，不改核心代码（开闭原则）。

## 3. 模块划分（M1–M6 与 Go 包映射）

| 模块 | 包路径 | 职责 |
|---|---|---|
| M1 接入层 | `cmd/` + `internal/server` | CLI、HTTP、MCP（SSE/stdio）、/openapi、/viz |
| M2 编排层 | `internal/scanner` + `scheduler` + `watcher` | 扫描、防抖调度、增量监听、事务 |
| M3 解析适配 | `internal/parser` + `parser/adapter/*` | 注册中心 + treesitter/scip/lsp/codegraph 适配器 |
| M4 AI 增强 | `internal/ai` | Tagger、增强、消歧、预算(Budget)管控 |
| M5 存储层 | `internal/store` + `vector` + `search` | file/sqlite/pg/redis + 向量 + 全文(FTS) |
| M6 服务层 | `internal/service` | 查询、裁剪、测试关联(5 策略)、影响面分析 |

数据流：
- **正向建索引**：源码 → 适配器解析 → 统一 IR → 存储层写入（+ 可选向量/全文）。
- **增强按需**：对缺 Tag/残缺实体，AI 按预算补全，失败不影响主流程。
- **反向服务 AI**：Agent 经 MCP/HTTP 查询 → 存储+裁剪 → 返回精准上下文。

## 4. 存储层设计（多驱动可插拔）

统一 `internal/store.Store` 接口；后端经 `cmd/codeschema` build-tag 分发（sqlite/pg 反向依赖 store，分发必须落 cmd 层否则循环依赖）。

| 驱动 | 配置 | 构建标签 | 说明 |
|---|---|---|---|
| file（默认） | `storage.driver=file` | 无 | JSON 文件，零依赖，fallback |
| sqlite | `storage.driver=sqlite` | 无 | modernc 纯 Go，关系查询/跨会话一致 |
| pg/postgres | `storage.driver=pg` + dsn | `-tags pg` | 亿级横向扩展（嵌入式 PG 集成测试） |
| Redis 缓存层 | `storage.kv=redis://...` | `-tags redis` | 热点类/调用反查 L2 缓存 |

> 实测关键结论（DEV_PROGRESS/scalebench）：
> - `UpsertIR` 逐文件多事务在 SQLite 上慢（10万≈77~237s）；**生产必须用 `BulkUpsert`（单事务+预编译）**，100k 落库降至 ~5~14s。
> - 内存：FileStore 100k≈1.08GB、chromem 100k≈169MB。
> - 规模决策：<1万 默认栈；1万~10万 SQLite+chromem；>10万 PG+Redis。

## 5. 解析适配层

- **统一 IR**：`IRDocument` + `ClassIR/MethodIR/ParamIR/CallIR`（`internal/parser/ir.go`）。
- **注册优先级链**：`CompositeResolver`（Go→Java→Gradle→启发式）；Go 模块路径精确匹配优先，Java 含 FQCN/通配符/标准库前缀过滤，Gradle 支持 `:module:path` 与白名单。
- **双路径**：默认纯 Go 正则轻量解析（30 语言，无 CGO）；`-tags treesitter` 切真语法树。
- **生产验证**：SCIP（真实 fixture 端到端、调用关系）、LSP（gopls/clangd 真实验证，`JSON-RPC` `omitempty` 修复等）、CodeGraph（真实 schema 优先、缺表显式降级不静默空 IR）。

## 6. 语义检索与全文搜索

- 双路检索：符号图精确检索（FTS/PersistentFTS）+ 向量语义检索（PersistentStore/ChromemStore/LocalEmbedder/ONNXEmbedder），融合重排（Reranker）。
- 嵌入模型：默认 `bge-small-zh-v1.5`（ONNX，`-tags onnx`）；自动检测模型，失败降级 LocalEmbedder。
- 实测：ONNX **Recall@1/@3/@5 = 1.00 全胜**；Local(TF-IDF) 0.42/0.58/0.83。语义敏感场景用 `-tags onnx`。
- 模型分发：注册表 URL + `make models-serve` 本地 HTTP 分发 + SHA-256 校验；下载支持断点续传。

## 7. 可观测性与健壮性

- 结构化日志（`log/slog`）、Prometheus 指标（`/metrics`）、链路追踪（`internal/trace`）。
- 生产级健壮性：优雅关闭（`internal/robust/graceful`）、指数退避重试、Panic 恢复、安全中间件（Bearer token/路径遍历防护）。
- build-tag 隔离 cgo：默认构建无 gcc 依赖。

## 8. 多租户（单实例多仓库）

- `internal/tenant.Manager` + `internal/runtime`：一进程按 `project` 路由多隔离仓库；每租户独立 store + 独立 FTS/向量/IDF 索引（未显式配置时按各自 dsn 派生，**保证索引隔离**）。
- 接入：`serve`/`mcp` 共用 `--config` 的 `tenants:` 列表；HTTP 用 `X-Tenant`/`?tenant=`，MCP 用 `project`；`list_projects`/`GET /projects` 枚举。
- 向后兼容：无 `tenants` 退化为单 `default` 租户。示例见 `build/mt-demo.yaml`。
