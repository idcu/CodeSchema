# P7 存储层（Store Layer）

> 模块编号：P7 ｜ 父模块：无（一级） ｜ 完成度：90%（file 100%，sqlite 92%，pg/redis 85%）

## 🎯 模块用途

系统数据的**权威持久化层**。以 `store.Store` 接口统一抽象，提供四个可插拔驱动：

| 驱动 | 场景 | 构建标签 |
|---|---|---|
| `file`（默认） | JSON 文件，零依赖 | 无 |
| `sqlite` | 关系查询 / 跨会话一致 | 无 |
| `pg` / `postgres` | 亿级横向扩展 | `-tags pg` |
| `redis` | 热点类/调用反查 L2 缓存 | `-tags redis` |

解决「文档声称 SQLite、现实仅 JSON」的历史实现落差，并给出从单机到亿级的存储演进路径。

## 🧱 拆分逻辑说明

按**技术分层（持久化）+ 多驱动插件**划分：核心定义 `Store` 接口（数据契约），四个驱动是其实现积木。**关键约束**：sqlite/pg 子包反向依赖 `internal/store`（实现其接口），因此驱动分发**必须落在 cmd 层**（`store_dispatch.go`），否则循环依赖——这是拆分时验证过的硬性边界。

## ⚙️ 技术说明

**技术选型**：默认 JSON 文件；`modernc.org/sqlite`（纯 Go 免 CGO）；`lib/pq`（pg）；`go-redis/v9`（redis）。

**对外接口契约（`store.Store`）**：

```go
Open/Close
UpsertFile/GetFileByPath/GetFileByID/DeleteFile/GetAllFiles
UpsertClasses/UpsertMethods/UpsertCalls
UpsertIR(ctx, *parser.IRDocument)        // 单文件增量入库
BulkUpsert(ctx, []*parser.IRDocument)    // 批量入库（消除事务放大）
GetClassesByFileID/GetMethodsByClassID/GetCallsByFileID
UpsertTags/UpsertMethodTags/SearchByTag/GetAllTagsWithCategories
HealthCheck
```

**依赖的下层模块**：P3_1（IR 数据结构契约）、P8 公共模块。
**被依赖方**：P2_1 Service、P2_2 Scanner、P4_1 Analyzer、P5_1 检索、P1_1 CLI（驱动分发）。

**数据模型**：`FileRecord`（含 content_hash/imports/language/parse_status）、`ClassRecord`、`MethodRecord`、`CallRecord`、标签映射。

## 🔄 替代方案

- 只用文件存储：关系查询与跨会话一致缺失，SQLite 是已确认的权威存储。
- 存储分发内联 `store.NewStore`：形成循环依赖，不可行——cmd 层分发是唯一正解。
- 未来亿级：PG（pgvector 语义向量演进）+ Redis 缓存层构成完整扩展路径。
