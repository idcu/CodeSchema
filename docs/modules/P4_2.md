# P4_2 AI 标签推导与测试关联

> 模块编号：P4_2 ｜ 父模块：P4 分析层 ｜ 完成度：85% ｜ 代码：`internal/ai`（tagger.go / enhancer.go / budget.go / client.go / http_client.go）

## 🎯 模块用途

引入 LLM 增强代码元数据的**语义质量**：AI 标签推导（在规则六类标签之外补全语义标签）、注释补全（EnhanceDoc）、同名方法消歧（Disambiguate，查询期选择正确候选）。带 token 预算控制与完整降级路径——未配置 LLM 或预算耗尽时，系统静默回退到规则推导，主流程零影响。

## 🧱 拆分逻辑说明

按**职责边界（非确定性推理）**独立：AI 是唯一依赖外部服务（LLM）的模块，失败/慢/贵是常态，必须与确定性核心（Analyzer）解耦。通过 `SetEnhancer`/`WithAIEnhancer` 注入而非硬依赖，未注入时所有调用方走规则路径。

## ⚙️ 技术说明

**技术选型**：OpenAI 兼容 HTTP 客户端（`/v1/chat/completions`，自实现 `http_client.go`，无 SDK 依赖）；`Budget` 预算器（scan/query 两个独立额度）；`Enhancer` 分阶段（扫描期标签 + 查询期消歧）。

**对外接口契约**：
- `NewOpenAICompatClient(HTTPClientConfig)` — 配置不全（缺 BaseURL/APIKey/Model）返回 nil（禁用）
- `NewBudget(perScan, perQuery)` — 预算控制（扫描期/查询期独立，`ScanRemaining`/`QueryExhausted`）
- `Enhancer.EnhanceTag(ctx, IRable)` / `EnhanceDoc` / `Disambiguate(ctx, candidates, hint)` — 三类增强
- `NewClassEntity`/`NewMethodEntity` — Store 记录适配 IRable

**依赖的下层模块**：P3_1（IR 结构）、P7 存储层（读候选记录）、P8_2 日志、P8_5 错误体系。

**数据模型**：`IRable`（class/method 适配接口）、`Phase`（扫描/查询）；无持久化模型。

## 🔄 替代方案

- 直接调各厂商 SDK（openai-go/anthropic-go）：厂商绑定且多 SDK 体积大；OpenAI 兼容协议是事实标准，自实现 HTTP 客户端最通用（兼容 DeepSeek/通义等）。
- 纯规则标签：无 AI 成本但语义覆盖差；当前「规则兜底 + AI 增强」是最优取舍。

## 📊 完成度：85%

已做：OpenAI 兼容客户端、预算控制（扫描/查询独立）、标签/注释/消歧三类增强、规则降级路径、mock LLM 单测全覆盖、**生产编排接入**（`Analyzer.SetEnhancer` 标签补全 + `Service.WithAIEnhancer` 查询期同名消歧，均 nil 安全降级）、Disambiguate 接入搜索处理器。
未做：**真实 LLM 服务下的系统性质量评估与调优**（标签准确率、预算策略）——需外部 API key，阻塞中；多 provider 配置验证。

## 🚧 阻塞与风险

- 依赖外部 LLM：无服务时降级规则推导，**降级后标签质量需在真实仓库评估**（主要风险）。
- token 预算策略（`BudgetPerScan`/`BudgetPerQuery`）参数需按仓库规模调优。
- 合规：发送代码片段到外部 LLM，需评估数据出域策略（当前由配置决定是否启用）。
