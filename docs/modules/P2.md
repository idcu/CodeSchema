# P2 编排层（Orchestration Layer）

> 模块编号：P2 ｜ 父模块：无（一级） ｜ 完成度：100%

## 🎯 模块用途

编排层是系统的「中枢神经系统」，负责两类业务链路的编排：

1. **写路径（增量更新链）**：Watcher 监听文件变更 → Scheduler 防抖合并 → Scanner 增量解析入库 → Service 增量重建索引。
2. **读路径（查询聚合）**：Service 聚合解析/检索/分析/存储四类能力，向接入层（MCP/HTTP）输出统一的查询结果。

解决「变更如何被发现、更新如何被调度、查询如何被聚合」的问题。

## 🧱 拆分逻辑说明

按**业务域（写路径/读路径）**划分：

- 写路径拆为三块——Watcher（发现变更）、Scheduler（合并防抖）、Scanner（执行解析入库）。三者是数据流上下游，但职责与生命周期完全不同：Watcher 长驻监听、Scheduler 负责时间窗口调度、Scanner 可被独立调用（scan 命令）。
- 读路径收敛为 Service 一个模块——它是接入层唯一的查询入口，负责把 Search/Analyzer/AI/Store 的原始能力组合成业务语义（上下文裁剪、影响面、关联测试）。

边界：编排层**不生产**任何代码元数据（那是 P3 的职责），只负责驱动与聚合。

## ⚙️ 技术说明

**技术选型**：Go 标准库 `context` + goroutine；无外部编排框架（无工作流引擎）。

**对外接口契约**：
- Service：`GetContext`/`GetImpact`/`GetTests`/`Search`/`GetCallGraph` 等 20+ 方法（见 P2_1）
- Scanner：`ScanAll`/`ProcessFile` + 索引回调 `SetOnIndex`/`SetOnDelete`（见 P2_2）
- Watcher：`Start(ctx)` 阻塞监听接口（见 P2_3）
- Scheduler：`Start(ctx, handler)` 防抖调度（见 P2_4）

**依赖的下层模块**：P3_1 解析核心（IR 消费）、P4_1 Analyzer、P4_2 AI、P5_1 检索、P7 存储层、P8 公共模块（log/metrics/trace/robust）。

**数据模型**：无自有持久化模型；运行时持有 Service 组件装配图。

## 🔄 替代方案

- 引入工作流引擎（Temporal/Cadence）做调度：对单机增量监听场景过重，当前 goroutine + context 足够。
- Scanner 与 Watcher 合并：会把「被动监听」和「主动扫描」耦合，导致 scan 命令无法复用增量逻辑，故拆开。
