# P7_2 SQLite 驱动

> 模块编号：P7_2 ｜ 父模块：P7 存储层 ｜ 完成度：97% ｜ 代码：`internal/store/sqlite`（sqlite.go 956 行）

## 🎯 模块用途

以 SQLite 作为**权威关系存储**：完整实现 `store.Store` 接口（文件/类/方法/调用/标签 + 反向查询 + `UpsertIR` 增量入库），消除「文档声称 SQLite、现实仅 JSON」的实现落差。`storage.driver=sqlite` 即启用。

## 🧱 拆分逻辑说明

按**部署单元（独立驱动积木）**独立：SQLite 是纯 Go 免 CGO 的关系型后端，与 file/pg/redis 并列。子包反向依赖 `internal/store`（实现接口），因此**不允许**在 `store` 包内 import 它，必须经 cmd 层分发。

## ⚙️ 技术说明

**技术选型**：`modernc.org/sqlite`（纯 Go 免 CGO）；`database/sql` 标准接口。

**对外接口契约**：实现 `store.Store` 全部方法；`UpsertIR`（单文件增量）+ `BulkUpsert`（批量单事务）。

**依赖的下层模块**：P3_1（IR）、P7_1（Store 接口）、`modernc.org/sqlite`。

**数据模型**：DDL 见 `internal/store/migrations/`；file/class/method/call/tag 表 + 反向引用表。

## 🔄 替代方案

- 只用 JSON 文件：无关系查询/跨会话一致，超大仓性能差（已实测单条 upsert 慢 500 倍）。
- 只用 PG：小中型部署过重；SQLite 是单机权威存储的正解。

## 📊 完成度：97%

已做：全接口实现、`UpsertIR`、`BulkUpsert`（N=10万 降至 5~14s）、与 file 驱动切换验证、WAL + synchronous=NORMAL + busy_timeout 配置、**并发安全验证**（纯写并发 + 读写并发 + 多读并发，均含 -race 通过——`TestSQLite_Concurrent*` 与 `TestConcurrentFixed_*`）。
未做：WAL 检查点参数在极端写负载下的调优（低优先级，可并入 scalebench）。

## 🚧 阻塞与风险

- 无阻塞。并发读写经 `-race` 验证无死锁、无数据竞争（store.mu 串行化所有 SQL 操作）。
- 单文件 DB 仍受 SQLite 写串行限制：高并发写入吞吐上限由 WAL + BulkUpsert 保证，亿级横向扩展走 PG（P7_3）。
- 经验教训：早期曾将「reader 无限循环测试超时」误判为驱动并发死锁，实为测试设计缺陷（reader 需固定迭代次数），已纠正并保留 `TestConcurrentFixed_*` 作回归。
