# P7_2 SQLite 驱动

> 模块编号：P7_2 ｜ 父模块：P7 存储层 ｜ 完成度：92% ｜ 代码：`internal/store/sqlite`（sqlite.go 956 行）

## 🎯 模块用途

以 SQLite 作为**权威关系存储**：完整实现 `store.Store` 接口（文件/类/方法/调用/标签 + 反向查询 + `UpsertIR` 增量入库），消除「文档声称 SQLite、现实仅 JSON」的实现落差。`storage.driver=sqlite` 即启用。

## 🧱 拆分逻辑说明

按**部署单元（独立驱动积木）**独立：SQLite 是纯 Go 免 CGO 的关系型后端，与 file/pg/redis 并列。子包反向依赖 `internal/store`（实现接口），因此**不允许**在 `store` 包内 import 它，必须经 cmd 层分发。

## ⚙️ 技术说明

**技术选型**：`modernc.org/sqlite`（纯 Go 免 CGO）；`database/sql` 标准接口。

**对外接口契约**：实现 `store.Store` 全部方法；`UpsertIR`（单文件增量）+ `BulkUpsert`（批量单事务）。

**依赖的下层模块**：P3_1（IR）、P7_1（Store 接口）、`modernc.org/sqlite`。

**数据模型**：DDL 见 `internal/store/migrations/`；file/class/method/call/tag 表 + 反向引用表。

## 🔄 替代方案

- 只用 JSON 文件：无关系查询/跨会话一致，超大仓性能差（已实测单条 upsert 慢 500 倍）。
- 只用 PG：小中型部署过重；SQLite 是单机权威存储的正解。

## 🚧 阻塞与风险

- ⚠️ **已知第三方库缺陷（阻塞项）**：`modernc.org/sqlite v1.56.0 + libc v1.74.4` 在 macOS 上，多 goroutine 访问 SQLite（即使 `database/sql` 单连接 + `store.mu` 严格串行）会触发 **libc 全局内存分配器（allocMu 保护 Xmalloc/Xfree）死锁/CPU 自旋**，查询永久卡死。原生 `database/sql` 最小可复现（`SELECT 1` 不触发、访问表的 SELECT + 任一其他 goroutine 活跃即触发）；`runtime.LockOSThread` 仅单 goroutine 有效。单 goroutine 使用完全正常。
  - **影响**：同进程并发场景（serve 多请求查询 + 后台扫描写入）存在卡死风险；多进程（每进程单 goroutine 访问）不受影响。
  - **处置**：`SetMaxOpenConns(1)` 已落地（避免放大）；`TestSQLite_ConcurrentReadWrite` 标记 Skip 并附复现说明；升级 modernc 或替换驱动（如 `ncruces/go-sqlite3`）后必须复测。
  - **替代方案**：高并发同进程场景暂建议使用 file 驱动或 PG（P7_3）。
