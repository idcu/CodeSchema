# P1 接入层（Interface Layer）

> 模块编号：P1 ｜ 父模块：无（一级） ｜ 完成度：100%

## 🎯 模块用途

接入层是 CodeSchema 系统对外暴露的全部协议入口，解决「AI 客户端 / 命令行 / 浏览器如何与系统交互」的问题。它把三种完全不同的交互协议——CLI 一次性命令、MCP 工具调用（面向 AI Agent）、HTTP RESTful + 可视化（面向浏览器/脚本）——统一转译为对下层 `Service` 的调用。

对应职责：协议适配与参数装配，**不承载任何业务逻辑**。

## 🧱 拆分逻辑说明

按**技术分层（协议入口维度）**划分。三个子模块的划分依据：

- 生命周期不同：CLI 命令执行完即退出；MCP/HTTP Server 是长驻进程，需处理优雅关闭、配置热重载。
- 协议形态不同：CLI 是 `flag` 参数解析 + 进程调用；MCP 是 JSON-RPC 2.0 + SSE/stdio 双向流；HTTP 是 RESTful 请求/响应。
- 客户端生态不同：MCP 面向 Claude Code / Cursor / VS Code 等 AI 工具；HTTP 面向脚本与浏览器；CLI 面向人工运维。

三者的边界：都只做「协议 → Service 方法」的转译与校验，不直接触碰 Store/Parser。

## ⚙️ 技术说明

**技术选型**：Go 标准库 `flag`、`net/http`；MCP 为手写 JSON-RPC 2.0 实现（无第三方 MCP SDK）。

**对外接口契约**：
- CLI：`codeschema {scan|watch|rebuild-kv|benchmark|mcp|serve|version}`（见 P1_1）
- MCP：11 个工具，`search_symbols`/`context`/`impact`/`tests` 等（见 P1_2）
- HTTP：RESTful 端点 + `/viz` 可视化 + `/openapi` 文档（见 P1_3）

**依赖的下层模块**：P2_1 Service（主入口）、P2_2 Scanner（scan/watch）、P8 全部公共模块（config/log/metrics/trace/robust）、P6_3 模型分发（接线向量栈）。

**数据模型**：无自有数据模型，透传 Service 的结果结构。

## 🔄 替代方案

- 用 `cobra`/`urfave/cli` 替换手写 `flag`：子命令帮助/补全体验更好，但引入额外依赖，当前 7 个子命令规模不值得。
- 用官方 MCP Go SDK（`mark3labs/mcp-go`）替换手写 JSON-RPC：协议演进同步更快，但当前 11 个工具均为自描述 JSON-RPC，迁移收益低。
- HTTP 用 `gin`/`chi` 框架：中间件生态丰富，但当前端点少、手写即可控。
