CodeSchema 技术路线 · 大白话版

一个「给 AI 当导览员」的工具 —— 用搭乐高的思路，把代码仓库整理成 AI 能直接查的地图

130 秒看懂它 不知道它干什么？只看这一节

一句话：AI 要回答代码问题，通常得把整个仓库翻一遍，又慢又费钱。 CodeSchema 提前把仓库拆成「类 / 方法 / 谁调用谁」这种积木块存起来，AI 问的时候直接查积木，不用再翻仓库。
输入
你的代码仓库（比如一个 Go 项目）
输出
一份结构化索引 + 一个 AI 能调用的接口（MCP）
效果
AI 回答代码问题更快、更准、更省 token

2一条流水线看懂全流程 数据从头到尾怎么走

整个系统就是一条 6 站流水线：仓库进去，接口出来。看懂这条线，就懂了大半。

第 1 站
📂 扫描
把仓库里所有文件列出来，没变过的跳过。
scanner · SHA-256 去重
第 2 站
🧩 拆解
把源码拆成积木：有哪些类、方法、调用了谁。
parser · tree-sitter 等
第 3 站
🕸️ 分析
画关系网：谁调谁、谁继承谁、改一处会影响哪。
analyzer · 4 张关系图
第 4 站
🗄️ 存档
积木存起来，重启不丢。
store · 默认 JSON 文件
第 5 站
🔍 建索引
给积木编目录：既能搜关键词，也能搜"意思相近"。
search + vector · 双路检索
第 6 站
🚪 开门
让人或 AI 来查：命令行、网页接口、AI 接口三选一。
CLI / HTTP / MCP

37 个零件盒（模块） 每个盒子只干一件事

每个「零件盒」对应代码里的一个大模块。颜色只是为了好记，不是技术分类。

① 扫描仪

负责"逛仓库"：把文件都找出来，内容没变的直接跳过，省时间。
internal/scanner · scheduler

② 解析器

负责"拆积木"：把代码变成类 / 方法 / 调用关系。这块有多个可换的拆法。
internal/parser · adapter

③ 分析引擎

负责"画关系网"：谁调谁、谁继承谁，改一处会炸到哪些地方。
internal/analyzer

④ 仓库（存档）

负责"存积木"：解析结果落地保存。有 4 种存法可选。
internal/store

⑤ 检索器

负责"找积木"：关键词搜 + 语义搜（意思相近也能找到），再融合排序。
internal/search · vector

⑥ 接口层（大门）

负责"开门"：三扇门——命令行、网页接口、AI 专用接口（MCP）。
internal/server

⑦ 后勤（底座）

负责"保运行"：配置、日志、监控、崩溃恢复，让整套系统稳稳跑。
config · log · metrics · robust

4哪些零件可以换？ 同一插槽、不同实现，插上去就能用

乐高的妙处：同一块底板，积木可换。下面每个「换装点」都有好几种实现，看状态挑。

换装点 默认用哪个 还能换什么 现在的坑 / 限制
存档方式 JSON 文件 ✅ 默认 SQLite ⚠️ 已接但慢 · PostgreSQL ⚠️ 未接主路 · Redis ⚠️ 仅缓存 SQLite 写入实测比 JSON 慢约 500 倍（10 万条：193 秒 vs 0.4 秒）；PG / Redis 代码写了但没接入默认入口
拆解方式 tree-sitter（轻量正则）✅ 默认 SCIP ✅ 已验证 · LSP ⚠️ 部分验证 · CodeGraph 🚧 骨架 默认方式只是"正则近似拆"，调用关系只有 Go / Python 较准；SCIP 要额外先产出 .scip 文件；CodeGraph 基本没做
语义搜索 Local（关键词近似）✅ 默认 ONNX 真语义模型 ⚠️ 需外置 默认方式"懂词不懂义"；ONNX 要自己下载 47MB 模型，且当前会导致编译强制依赖 gcc
监听文件变化 轮询（定时看）✅ 默认 fsnotify（系统通知）✅ 可选 无

图例：✅ 能直接用　⚠️ 能用但有限制　🚧 没做完

5现在能用到什么程度？ 红绿灯一览

🟢 能直接用的：
扫描 → 解析 → 分析 → 存档（JSON）→ 双路检索 → 命令行 / HTTP / MCP 三个接口，整条线已打通并通过测试。
代码能编译通过（go build ./...）；SCIP / LSP 已用真实语言服务器验证过，能拿到真实的类和方法。
🟡 能用但有限制：
• ONNX 真语义搜索：模型要自己下，且默认构建会因此强制依赖 gcc（和 README 说的"GCC 可选"不符）。
• SQLite 存档：能切换，但写入太慢，暂达不到"生产级"（README 的表述和实测相反）。
• 向量可视化页（/viz）：只有 Chromem 一种存储支持。
• LSP 解析：缺项目上下文时会悄悄跳过（clangd 常见）。
🔴 还没做完的：
• CodeGraph 解析器：只有骨架，基本不可用。
• 测试关联（给类 / 方法关联单测）：显式注解、覆盖率、AI 增强都还没实现。
• PostgreSQL / Redis 存档：代码写好了，但没接进主入口，等于没上线。

6两个大坑，先知道 和文档描述不一致的地方

坑一：SQLite 实际比 JSON 慢得多。
实测 10 万条数据写入：SQLite 约 193 秒，JSON 约 0.4 秒，差约 500 倍。 但 README 头部仍写着"SQLite 是生产级权威存储、JSON 只是兜底"——和实测正好相反。 结论：目前 JSON 才是能打的那个，SQLite 写入路径需要优化。
坑二：默认编译其实强制要 gcc（CGO）。
代码里无条件引用了 ONNX 库，所以哪怕你不用 ONNX 模型，编译也需要 gcc。 README 写"GCC 可选"是不准确的。

7怎么开始用？ 三步走

  1. 扫一遍仓库：运行 codeschema scan ./你的项目，系统自动完成 扫描 → 拆解 → 分析 → 存档。
  2. 打开大门：codeschema serve 起网页接口；codeschema mcp 起 AI 专用接口；codeschema watch 监听文件变化、自动增量更新。
  3. 让 AI 来问：把 MCP 接口接给 AI，之后 AI 回答你代码问题时，就会先查这份索引，而不是翻整个仓库。
