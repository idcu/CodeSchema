一个「给 AI 当导览员」的工具 —— 用搭乐高的思路，把代码仓库整理成 AI 能直接查的地图

130 秒看懂它 不知道它干什么？只看这一节

一句话：AI 要回答代码问题，通常得把整个仓库翻一遍，又慢又费钱。 CodeSchema 提前把仓库拆成「类 / 方法 / 谁调用谁」这种积木块存起来，AI 问的时候直接查积木，不用再翻仓库。
输入
你的代码仓库（支持 30 种语言，含 Go / Java / TS / Python 等）
输出
一份结构化索引 + 一个 AI 能调用的接口（MCP）
效果
AI 回答代码问题更快、更准、更省 token

2一条流水线看懂全流程 数据从头到尾怎么走

整个系统就是一条 6 站流水线：仓库进去，接口出来。看懂这条线，就懂了大半。

第 1 站
📂 扫描
把仓库里所有文件列出来，没变过的跳过（内容哈希去重）。
scanner · SHA-256 去重
第 2 站
🧩 拆解
把源码拆成积木：有哪些类、方法、调用了谁。默认纯 Go 正则（30 语言），可切真语法树。
parser · 30 语言 · 双路径
第 3 站
🕸️ 分析
画关系网：谁调谁、谁继承谁、改一处会影响哪。
analyzer · 关系图
第 4 站
🗄️ 存档
积木存起来，重启不丢。SQLite / JSON / PG / Redis 四种存法。
store · 批量写入已优化
第 5 站
🔍 建索引
给积木编目录：既能搜关键词，也能搜"意思相近"（本地 ONNX 真语义模型，已跑通）。
search + vector · 双路检索
第 6 站
🚪 开门
让人或 AI 来查：命令行、网页接口、AI 接口三选一（共 6 个命令）。
CLI / HTTP / MCP

37 个零件盒（模块） 每个盒子只干一件事

每个「零件盒」对应代码里的一个大模块。颜色只是为了好记，不是技术分类。

① 扫描仪

负责"逛仓库"：把文件都找出来，内容没变的直接跳过，省时间；还负责监听文件变化做增量更新。
internal/scanner · scheduler

② 解析器

负责"拆积木"：把代码变成类 / 方法 / 调用关系。默认纯 Go 正则（30 语言，免 CGO），-tags treesitter 切真语法树（精度双档满分）。
internal/parser · adapter

③ 分析引擎

负责"画关系网"：谁调谁、谁继承谁，改一处会炸到哪些地方。
internal/analyzer

④ 仓库（存档）

负责"存积木"：解析结果落地保存。SQLite（纯 Go，批量写入已优化）/ JSON / PG / Redis 四种存法，均可用。
internal/store

⑤ 检索器

负责"找积木"：关键词搜（纯 Go 全文索引）+ 语义搜（本地 ONNX bge-small-zh，真实推理已跑通），再融合排序。
internal/search · vector

⑥ 接口层（大门）

负责"开门"：三扇门——命令行、网页接口、AI 专用接口（MCP）。
internal/server

⑦ 后勤（底座）

负责"保运行"：配置、日志、监控、崩溃恢复、模型分发，让整套系统稳稳跑。
config · log · metrics · robust

4哪些零件可以换？ 同一插槽、不同实现，插上去就能用

乐高的妙处：同一块底板，积木可换。下面每个「换装点」都有好几种实现，看状态挑。

换装点 默认用哪个 还能换什么 现在的坑 / 限制
拆解方式 纯 Go 正则（30 语言）✅ 默认 真语法树 ✅ -tags treesitter · SCIP ✅ 已验证 · LSP ⚠️ 部分验证 默认方式"正则近似拆"，复杂语法（重载/链式/模板特化）不如真语法树准；真语法树需 CGO 编译

5现在能用到什么程度？ 红绿灯一览

🟢 能直接用的：
扫描 → 解析（30 语言）→ 分析 → 存档 → 双路检索 → 命令行 / HTTP / MCP 三个接口，整条线已打通并通过测试。
ONNX 语义检索本机端到端跑通（真实嵌入 dim=512）；SQLite / PG / Redis 存档均可用；模型分发本地闭环（本地模型零下载、打包产物零配置分发）。
🟡 能用但有限制：
• 真语法树（-tags treesitter）与 ONNX（-tags onnx）需要 CGO 编译，且 ONNX 需对应平台的动态库。
• LSP 解析：缺项目上下文时会悄悄跳过（clangd 常见）；已接入 Registry 编排主路（失败自动回退 tree-sitter）。
• 模型公网分发已闭环（注册表 URL 回填 + make models-serve）；Docker 实构建 / PG- Redis 实跑待网络恢复。
🔴 还没做完的：
✅ 已全部清零（2026-08-15）——
• CodeGraph 解析器：已校准真实 schema（nodes/edges 真实 DDL 双契约自适应），可当正式数据源；
• codeschema benchmark 子命令：已落地（CLI 6→7 命令，多仓库对比报告）。

6曾经的两个大坑，现在怎么样了 踩过、填平了

坑一（已填平）：SQLite 写入比 JSON 慢 500 倍。
8/14 实测 10 万条数据写入：SQLite 约 193 秒，JSON 约 0.4 秒。已实现 BulkUpsert（单事务 + 预编译语句）， 10 万条落库降至 5~14 秒（约 10 倍提速），并固化进 CI 看护回归。SQLite 现已可作正式存档。
坑二（已填平）：默认编译强制要 gcc（CGO）。
原来无条件引用 ONNX 库导致 go build ./... 就要 gcc。已用 //go:build onnx 隔离—— 默认构建纯 Go 免 CGO；只有显式 -tags onnx 才引入 ONNX（此时才需要 gcc + 动态库）。

7怎么开始用？ 三步走

  1. 扫一遍仓库：运行 codeschema scan ./你的项目，系统自动完成 扫描 → 拆解 → 分析 → 存档。
  2. 打开大门：codeschema serve 起网页接口；codeschema mcp 起 AI 专用接口；codeschema watch 监听文件变化、自动增量更新。
  3. 让 AI 来问：把 MCP 接口接给 AI，之后 AI 回答你代码问题时，就会先查这份索引，而不是翻整个仓库。
