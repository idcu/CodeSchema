# CodeSchema · AI 编程工具协作规范

> 写给谁：对接本项目的所有 AI 编程工具（Trae / WorkBuddy / Cursor / Copilot / Claude Code 等）与开发/评审人员
> 写什么：AI 读档 → 领任务 → 编码 → 同步文档 → commit 的全流程约束，以及人工复核边界
> 核心原则：AI 先"读懂项目"再动手；代码变，文档跟着变；Commit 即档案
> 优先级：P0
> 最后更新：2026-08-17

---

## 0. 本规范与系统联动

本系统本身就是"服务 AI 的代码上下文工具"。AI 有双重身份：

- **协作开发本系统**时：以本文档为流程约束，按 §1 的文档读取顺序理解项目。
- **探究本系统自身能力**时：可启动 CodeSchema MCP，用 `context` / `impact` / `search_symbols` / `get_tags` / `tests` 拉取代码上下文辅助理解。

进行开发任务时以本规范为准；涉及系统单点能力探究时可叠加 MCP 查询。

---

## 1. AI 启动阶段 —— 读哪些文档（顺序即优先级）

| 顺序 | 文档 | AI 获取什么 |
|---|---|---|
| 1 | `docs/README.md` | 系统定位、技术栈、目录导航 |
| 2 | `docs/1-生产层/技术设计文档.md` | 架构、模块划分、数据流、关键流程 |
| 3 | `docs/1-生产层/代码规范与开发指南.md` | 目录、命名、分支、commit、构建/启动 |
| 4 | `docs/1-生产层/API文档.md` | 接口约定（涉接口开发才读） |
| 5 | `docs/1-生产层/数据库设计.md` | 表结构、DDL（涉存储才读） |
| 6 | `DEV_PROGRESS.md` / `CHANGELOG.internal.md` | 近期改动、已知进度、历史坑 |
| 7 | 当前任务卡 / Issue 描述 | 本次做什么、验收标准 |

> 约束：完成读取前禁止写代码；确有歧义先提问，不得凭空臆造架构与命名。

---

## 2. 任务领取阶段 —— 任务从哪来

- 任务来源统一为：需求文档 / Issue / 任务看板 / 任务卡，至少包含：**目标、验收标准、涉及模块、关联文档**。
- AI 领到任务先解析"涉及模块"，据此决定读取对应模块文档（`docs/1-生产层/modules/`）。
- 验收标准不清晰 → 提问确认后再动手，不得自行扩大范围或降低标准。

---

## 3. 编码阶段 —— 遵循哪些约束

- 严格遵循《代码规范与开发指南》：命名、目录、代码风格、Go 惯例、注释语言（中文）。
- 新增模块 / 接口 / 表结构 → 先对照《技术设计》《API》《数据库设计》，不得重复造轮子。
- **破坏性变更**（改接口签名、改表、改配置、改 CLI 行为）必须先标注影响范围，**停止并等待评审，不得擅自改动**。
- 存储接线注意：sqlite / pg / redis 需经 `cmd/codeschema` 的 build-tag 分发（防循环依赖）；默认构建必须免 CGO（ONNX 走 `-tags onnx`）。
- 遵循**零造假红线**：不做无数据支撑的性能结论；改动必跑对应测试/基准，且如实报告结果。
- 复用优先：新增时主动识别可复用的公共类型 / 函数 / 常量，不重复实现；公共抽象调整影响现有调用方时必须显式说明影响范围。

---

## 4. 完成后 —— 同步更新文档（改码必改档）

| 代码变更 | 必须同步更新的文档 |
|---|---|
| 新增/修改功能 | 用户操作手册、系统简介（功能清单段） |
| 新增/修改接口 | API文档、客户端接入指南（如 MCP 工具变化） |
| 新增/修改表结构 | 数据库设计 |
| 架构/模块调整 | 技术设计文档 |
| 部署方式变更 | 部署手册、docker-compose / Dockerfile 注释 |
| 新增配置项/环境变量 | 配置参考、config.yaml.example、DEV_PROGRESS |
| 修复重要 bug | 版本发布说明、CHANGELOG.internal |
| CLI/行为变更 | 用户操作手册、README 快速开始 |

> 自检流程：完成编码后自问"本次改动影响哪些文档"，一并修改，与代码**同次提交**。禁止只改码不改档。

## 5. 提交阶段 —— Commit 规范（Conventional Commits）

- 类型：`feat / fix / docs / style / refactor / perf / test / chore`，可带 scope。
- 本次含文档更新 → 类型用 `docs`，或摘要中注明"含文档同步"。
- 示例：
  - `feat(user): 新增批量导出 + 同步更新用户操作手册`
  - `docs(api): 补全 search_symbols 参数与返回`
  - `fix(auth): 修复 token 刷新失效（含安全设计同步）`
- Body 携带关键验证数据：如 `heapUsed +2.20MB / P95 <50ms / 31 包测试全绿`。
- 禁止水 commit（如 `fix bug`、`update`、`optimize`）。
- 仅 `git commit`；**除非明确说 push，否则不 push**。

## 6. 人工复核边界

**AI 可自主完成**：读档 → 理解任务 → 编码 → 同步文档 → 本地自测（`go build` / `go vet` / `go test ./...`）→ commit。

**必须人工介入**：
- 合并到主分支的 PR 评审；
- 生产环境部署；
- 安全 / 合规相关变更；
- 破坏性接口 / 表 / 配置变更。

**人工复核重点检查**：
1. AI 是否同步更新了本次影响的文档；
2. commit message 是否准确、类型是否合规；
3. 验证数据是否为真实跑出的（非编造）。

AI 提出但未经评审的破坏性改动，应显式输出"存在破坏性变更，需人工确认"，不得静默提交。

---

## 7. 本规范自身维护

- 本规范自身也是文档：修改它的流程、或改动 `docs/*` / `scripts/*` 的业务逻辑时，同样按 §4 评估影响并同步。
- 提交遵循 §5。需求变化导致本体（AI 全流程）改变时，在此追加修订记录。
