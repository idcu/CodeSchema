4Phase 1：红灯笼清零 第 1-3 周 · 先处理技术路线上「没做完」的事

⑥ 接口层 T1-1 codeschema benchmark 子命令

现状：技术路线红灯笼①。CLI 仅 6 命令（scan/watch/rebuild-kv/mcp/serve/version），benchmark 能力散落在 internal/integration 测试与 make bench，用户无法一键对任意仓库出报告。
关键动作：
  • 新增 codeschema benchmark [--repo PATH] [--out build/bench.json] 子命令
  • 复用 internal/integration/benchhelper.go（NewBenchSetup/DiscoverGoFiles）+ benchreport.go（Markdown/JSON 对比报告）
  • 支持多仓库（继承 CODESCHEMA_BENCH_REPOS 分号分隔）与单仓模式
  • 输出扫描耗时/索引耗时/P50-P95 搜索延迟/内存快照，固化 JSON 落盘
验收：codeschema benchmark ./repo 输出 JSON+Markdown 报告；对本仓与 idcu-panel/backend 复现线性扩展结论；CLI 命令数 6→7；单测覆盖
依赖：无（复用现有 bench 基建）｜规模：M｜优先级：P0
✅ 已实施 — CLI 6→7 命令，多仓库对比报告（commit d617a77）

② 解析器 T1-2 CodeGraph 真实 schema 校准

现状：技术路线红灯笼②。已从「静默空 IR」修复为「缺表显式报错 + 按假设契约尽力读取」，但 symbols/edges 列名为假设（name/qualified_name/kind/file_path/language），未在本仓外确认。
关键动作：
  • 用真实 CodeGraph（github.com/gaurav-nelson/github-action-markdown-link-check 类工具的 codegraph CLI）导出 DB 样本
  • 比对假设列名 vs 真实 DDL，更新 internal/parser/adapter/codegraph/ 契约 SQL
  • 补真实 fixture 端到端测试（class/method/调用边真实提取）
  • 列漂移仍显式报错并降级 tree-sitter（保持「绝不静默空 IR」）
验收：真实 CodeGraph DB 上 ParseAll 返回真实类/调用 IR；契约表与 README 登记真实列名；测试全绿
依赖：需要 CodeGraph 工具或样本 DB｜规模：M｜优先级：P0
✅ 已实施 — nodes/edges 真实 DDL 双契约自适应（commit d9aa484）

② 解析器 T1-3 LSP 适配器接入 Registry 编排主路

现状：黄灯②。LSP 为独立子包，parser.Registry 的「首选 ErrSourceUnavailable → Select 回退 tree-sitter」链路未在生产编排串联；gopls 已端到端验证（PASS），clangd 缺上下文优雅跳过。
关键动作：
  • 将 LSP 适配器注册进 parser.Registry，配置开关（如 parser.lsp=true）控制启用
  • 按语言分发：Go→gopls / Java→jdtls / C/C++→clangd，缺工具优雅跳过并记录指标
  • 复用既有探测（compile_commands.json）、重试（robust.Retry）、空符号告警
  • 扫描路径打通：LSP 失败 → 自动回退 tree-sitter 正则，全链路可观测
验收：配置启用后 Go 仓库走 gopls 解析（类/方法真实返回）；无 gopls 环境自动回退正则并 WARN；-race 测试全绿
依赖：T1-2 无｜规模：L｜优先级：P1
✅ 已实施 — FallbackParser 降级回退 + 修复 scan 空 Registry（commit ec57a45）

  • scalebench 补 FileStore 大 N 内存实测表
验收：并发写不损坏；大仓建议（N>阈值切 SQLite）有实测数据支撑并写入 docs/dev/12
依赖：无｜规模：M｜优先级：P1
✅ 已实施 — flock 进程锁 + 原子写（commit 9594342）

LSP 进程管理复杂（子进程生命周期/资源泄漏）中 T1-3 引入不稳定因素 默认关闭、配置开启；复用 robust.Retry 与既有探测/告警；超时强杀；CI 用 mock + gopls 双覆盖
超大仓内存不可控（chromem 内存模式）高 T3-1 暴露 10万+ 内存爆炸 压测先行，给「何时切 SQLite/PG/chromem 持久化」决策表；必要时默认改持久化模式
公网制品托管不可用/带宽受限中 T2-1 无法验证公网拉取 本地分发已闭环不阻塞；公网 URL 先登记，验证可延后到环境允许；降级 LocalEmbedder 兜底
Docker 环境不可用中 T3-2/T3-3 阻塞 CI 上开 Docker job；本地无 Docker 时以 CI 为准，保留语法校验

11执行建议 怎么把计划落地

  1. 先做 T1-1（benchmark 子命令）：它复用现有基建、成本低、验收清晰，且是 Phase 3 压测的地基，先修路再跑车。
  2. T1-2 与 T1-3 并行推进：一个偏数据契约、一个偏编排链路，互不依赖；若 CodeGraph 样本拿不到，先把 LSP 主路打通。
  3. 每个任务按「验收标准」交付：任务完成 = 单测 + 实测数据 + 文档同步，三件套缺一不可（延续项目既有习惯）。
  4. 阶段末强制收口：每阶段结束跑一遍 make test + make test-race + make bench，更新 DEV_PROGRESS.md 与 CHANGELOG.internal.md。
  5. 不追求全做完：P0（T1-1/T1-2/T3-1）与 P1 是主路，P2/P3 可随时停；计划支持「任何阶段停下来的产品都可用」。
