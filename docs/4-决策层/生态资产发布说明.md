# 生态资产发布说明

> 写给谁：生态建设者、开源负责人、对外发布执行者
> 写什么：把仓库内已沉淀的可复用能力（解析适配器 / 编排 SDK / 工具链 / 配置预设）清单化，明确对外发布形态、复用入口与心智占位
> 核心原则：资产化 = 接口稳定 + 文档入口 + 发布形态明确，三者缺一不算资产
> 优先级：P2
> 最后更新：2026-08-18
> 来源：`analysis/2026-08-17-competitor-and-harness-analysis.md` §3.3 建议 7（生态资产化）

---

## 1. 为什么做资产化

竞品 CodeGraph（47.4K★）/ GitNexus（42K★）已验证「本地预计算结构 + MCP 供给 + 零代码出境」是 2026-08 的赢家路径。CodeSchema 能力同向，但能力全部藏在单仓库内，外部无法复用、无法形成心智份额。

资产化的目标：**把"代码上下文原语"能力拆成可独立对外发布的资产包**，让第三方（IDE 插件、agent 运行时、其他索引服务）按接口接入，而不是只把整个 monorepo 发布成一个二进制。

## 2. 资产清单（当前已沉淀，按发布优先级排序）

### A 级：解析适配器（最易资产化，直接抢占"结构解析原语"）

| 资产 | 位置 | 形态 | 复用入口 | 说明 |
|---|---|---|---|---|
| tree-sitter 适配器 | `internal/parser/adapter/treesitter` | ParserPlugin（30 语言，零 CGO 正则兜底） | `parser.Registry.Register` | 已实现，含 AST 调用图与 sanitizer |
| SCIP 直读适配器 | `internal/parser/adapter/scip` | 读 scip-java/go/clang/typescript 索引文件 | `parser.Registry.Register` | 精确符号/引用，失败自动降级 |
| LSP 适配器框架 | `internal/parser/adapter/lsp` | 子进程 JSON-RPC 2.0（gopls/jdtls/clangd） | `parser.Registry.Register` | 通用框架，可扩展任意 LSP |
| CodeGraph 直读适配器 | `internal/parser/adapter/codegraph` | 直读 CodeGraph SQLite（真实/历史双 schema 兼容） | `parser.Registry.Register` | 竞品数据源互操作 |
| 适配器注册中心 | `internal/parser/registry.go` | `Registry.Register/SetPriority/Select` | 语言 → 优先级链 | SCIP > LSP > 竞品直读 > tree-sitter |

**发布形态建议**：每个适配器独立为一个 Go 包 + 独立 `README.md` + 接口契约（`ParserPlugin` 只需实现 4 个方法）。对外可发布为 `github.com/idcu/codeschema-adapter-*` 独立仓库，或合并为一个 `adapterx` 聚合包。

> **进度（2026-08-17）**：A 级聚合包骨架已落地 `contrib/adapterx/`（自包含、仅依赖标准库）——统一契约 `ParserPlugin`/`BatchParser`、对外 DTO `IRDocument`、注册中心 `Registry`、发布元数据 `BuiltinAdapters()`；`internal/parser/adapterx.go` 提供 `ToAdapterX`/`FromAdapterX` 双向桥接。可直接拷贝为独立仓库 `github.com/idcu/codeschema-adapterx` 发布，第三方可按契约自行实现接入。

### B 级：编排层能力（资产化价值高，面向 agent/服务编排）

| 资产 | 位置 | 形态 | 复用入口 | 说明 |
|---|---|---|---|---|
| context-sdk | `internal/contextsdk` | 程序化编排 API | `NewClient(resolve).Compose(...)` | 一次调用组合多租户 × 多符号 × 影响面 × 关联单测 |
| 能力层 preset | `internal/config/preset.go` | YAML 一键组合 | `config.ApplyPreset(cfg)` | minimal / semantic / multitenant |
| 上下文追溯 | `internal/service`（TraceEntry） | 每次注入附 `_trace` | `ContextOptions.IncludeTrace` | 对齐 dsh append-only 轨迹 |
| 极简上下文模式 | `internal/service`（ModeMinimal） | 仅符号元数据、零文件 IO | `mode=minimal` | token 评测基线（100 符号批量：31× 快、8.7× 省内存） |

**发布形态建议**：context-sdk 是最值得先独立发布的编排资产——对外提供稳定 API 即可让任何 agent 运行时（dsh Code mode、Claude Code、自研 harness）一次拿到完整上下文包。

> **进度（2026-08-17）**：B 级发布评估骨架已落地 `contrib/contextsdk/`——`SDKProvider` 最小契约接口（`GetContextMode`/`GetImpact`）+ 公开 DTO（`SymbolContext`/`ImpactResult`/`Request`/`Package`/`TraceEntry`）+ 完整编排实现（`Client.Compose`，仅依赖标准库、自包含）+ 发布评估 README。**阻塞项已解除**：`contrib/contextsdk` 已实现为权威契约（可独立编译/测试/发布）；`internal/contextsdk` 改造为纯适配层，经 `ServiceProvider` 把 `internal/service.Service` 桥接为 `SDKProvider`，`NewClient` 签名保持向后兼容（仍接受 `func(tenant string) (*service.Service, error)`）。`contrib/contextsdk` 新增 11 条 mock 编排测试验证自包含约束，`internal/contextsdk` 集成测试（真实 Store+Analyzer）全通。下一步：P2 阶段按首个 v* tag 发布独立 module `github.com/idcu/codeschema-contextsdk`。

### C 级：工具链与集成资产

| 资产 | 位置 | 形态 | 复用入口 | 说明 |
|---|---|---|---|---|
| benchtrend | `scripts/benchtrend` | `make bench-trend` → HTML 精度趋势报告 | `go run ./scripts/benchtrend` | 纯标准库，JSONL 历史 → SVG 折线 |
| dsh 插件接入 | `contrib/dsh` | dsh 集成指南 + 配置模板 | 12 个 MCP 工具作能力插件 | stdio / SSE 双方式 |
| AGENTS.md | 仓库根 | 面向 agent 的协作约定 | 接入 agent 自动遵循 | 对齐 dsh 约定 |
| 多租户 | `internal/tenant` + `internal/runtime` | 单实例多项目隔离 | `tenant.NewManager` | 不改 Store 接口，纯路由层 + 多份单租户实例 |

**发布形态建议**：benchtrend 可独立为 CLI 工具（`codeschema benchtrend` 或独立仓库）；dsh 接入以 `dsh-plugin` topic 发布，抢占 dsh 的"代码理解"盲区。

## 3. 资产发布路线图（按投入产出比排序）

1. **先做入口，后做拆分**（低成本、纯增量）：
   - 在 `docs/3-使用层/用户操作手册.md` 增加「生态资产」章节，列明上述 A/B/C 三级资产的复用入口（本次文档即起点）。
   - 为 `contextsdk` 与每个适配器补充包级文档注释中的"对外复用示例"。
2. **独立发布 A 级适配器**：以 `codeschema-adapterx` 聚合包形式发布，附 4 个适配器的独立 README 与示例；这是抢占"结构解析原语"心智的最小可发布单元。
3. **独立发布 B 级 context-sdk**：稳定 API 后作为独立 Go 模块发布，供 agent 运行时依赖。
4. **dsh-plugin 上架**：把 12 个 MCP 工具以 dsh 插件形态发布，作为 CodeSchema 的对外分发渠道（对应建议 1）。
5. **引入对外基准**：把 minimal/full 对照（token 节省 + 任务质量）固化为可复现基准，对外背书"精准裁剪省 token"（补 §2.5 短板，对应建议 4）。

## 4. 资产化纪律（防"资产腐烂"）

- **接口即契约**：任何 A/B 级资产的对外方法签名变更，必须同步更新本档 + 对应包文档 + CHANGELOG.internal.md（沿用 `docs/AI协作规范.md` §4 的 14 类映射）。
- **入口唯一**：每个资产在本文档有唯一一行「复用入口」，代码中该入口的文档注释必须可点可查。
- **验证不丢**：资产拆分/发布前，必须跑对应包的 `go test` 与 benchmark，数据写入 CHANGELOG.internal.md（红线：没有数据就是没做）。
